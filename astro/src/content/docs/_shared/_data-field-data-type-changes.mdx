
FusionAuth provides **`data`** fields on many types of objects, including Applications, Tenants, Groups, Users, Registrations, Entities, and Consents.

When you use the Elasticsearch search engine, Elasticsearch indexes the **`user.data`**, **`registration.data`**, and **`entity.data`** fields. Elasticsearch requires a field to have the same data type across all indexed objects. After Elasticsearch indexes a field as one type, Elasticsearch expects every later value of the field to have the same type.

For example, you might store a boolean in **`user.data.migrated`**. If you later set **`user.data.migrated`** to an object for one User, searches no longer find that User. Searches still find other Users, as long as **`user.data.migrated`** holds a boolean or no value.

Keep the data type of each field consistent across objects. FusionAuth doesn't enforce the type, so the software that updates **`data`** fields must enforce the type. For the request to add enforcement to FusionAuth, see [GitHub issue 1149](https://github.com/FusionAuth/fusionauth-issues/issues/1149).

Keep a consistent schema in every **`data`** field, even when you use the database search engine:

* Elasticsearch may index other **`data`** fields in future versions of FusionAuth.
* When you switch from the database search engine to the Elasticsearch search engine, Elasticsearch indexes your existing data. Inconsistent types then hide objects from searches.

Store only valid dates in **`data`** fields. Elasticsearch fails to parse a date such as `0000-00-00`, which some databases return for an invalid timestamp. Set an invalid date to `null` instead.

When the types in **`data`** fields are inconsistent, searches silently skip objects, and Elasticsearch can throw a [MapperParsingException](/docs/deploy/troubleshoot/troubleshooting#mapperparsingexception).
