During logins, password changes, and [MFA Status API](/docs/apis/two-factor/retrieve-multi-factor-status) calls, FusionAuth decides whether to challenge the user with one of the user's MFA methods. With this lambda, you can change FusionAuth's MFA decision for the user or trigger a suspicious login event.

The MFA Requirement Lambda has access to the following information:

* the access token returned by FusionAuth as the result of a successful authentication
* the action being taken
* FusionAuth's out of the box MFA decision
* the user record
* the user's registration for the application they're trying to authenticate to
* the MFA policy settings on the tenant and application
* metadata about the request

You can use Lambda HTTP Connect to access external resources from this lambda. Keep external calls to a minimum, because every delay slows the request for your users.

## Lambda Structure

All lambda implementations must contain a method with the following signature:

```javascript
function checkRequired(result, user, registration, context) {
  // Lambda code goes here
}
```

The `checkRequired` function must accept the following parameters:

* `result`: an object used for returning modified MFA requirements back to FusionAuth.
* `user`: the read-only FusionAuth User object.
* `registration`: the FusionAuth `UserRegistration` object. This parameter is `null` when the request doesn't include an application, or when the user isn't registered for the application, such as when an existing user logs in to an application with SSO for the first time. This object is read-only.
* `context`: an object containing context for the current request. This object is read-only and contains several optional fields.

For more information about `user` and `registration`, see the [User API](/docs/apis/users) and [Registration API](/docs/apis/registrations) documentation.

`result` is of type `RequiredLambdaResult`, with the following structure:

```javascript
class RequiredLambdaResult {
    /**
     * This value will be set to FusionAuth's out of the box decision on whether an MFA challenge
     * should be required for the user. Mutate this to change the decision.
     * @type {boolean}
     */
    required;

    /**
     * To force a suspicious login event to be created, set this to true. This will have no effect
     * unless the action is `login`.
     * @type {boolean}
     */
    sendSuspiciousLoginEvent;
}
```

## Errors and Ignored Results

If the lambda throws an exception, FusionAuth requires MFA and writes the exception to the [Event Log](/docs/deploy/troubleshoot/troubleshooting#event-log).

For the `login` and `changePassword` actions, FusionAuth ignores the lambda's result when the Tenant has no MFA methods enabled. FusionAuth then doesn't send a suspicious login event either. For the `stepUp` action, FusionAuth always uses the lambda's result.

## Assigning The Lambda

After you create the lambda, assign the lambda to a Tenant. In the Admin UI, find the **MFA requirement lambda** field on the <Breadcrumb>Multi-Factor</Breadcrumb> tab of the Tenant configuration.

With the Tenant API, set **`tenant.lambdaConfiguration.multiFactorRequirementId`** to the lambda Id.

You can also assign a lambda to an application. An application lambda requires the Application MFA feature, which is part of the Enterprise plan. Without the feature, FusionAuth returns a validation error when you save the application. When the request includes an application with an assigned lambda, FusionAuth runs the application's lambda instead of the Tenant's lambda for every action. When the application has no lambda assigned, FusionAuth runs the Tenant's lambda. When the Tenant has no MFA methods enabled, FusionAuth always runs the Tenant's lambda. In the Admin UI, find the **MFA requirement lambda** field on the <Breadcrumb>Multi-Factor</Breadcrumb> tab of the Application configuration.

With the Application API, set **`application.lambdaConfiguration.multiFactorRequirementId`** to the lambda Id.
