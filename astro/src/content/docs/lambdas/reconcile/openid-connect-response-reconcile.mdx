## Lambda Structure

When you create the lambda with the API, give the function the following signature:

```javascript
function reconcile(user, registration, jwt, id_token, tokens, context) {
  // Lambda code goes here
}
```

This lambda must contain a function named `reconcile` that accepts the following parameters:

<ReconcileLambdaUserRegistrationParameters />
* `jwt`: the JSON payload returned from the OpenID Connect UserInfo endpoint. This object is read-only.
* `id_token`: the JSON payload returned in the `id_token`, or `null` when the `id_token` is not available. This object is read-only. &nbsp;<AvailableSince since="1.31.0"/>
* `tokens`: an object containing the encoded versions of the `access_token` and optionally the `id_token` when available. This object is read-only. &nbsp;<AvailableSince since="1.48.0"/>
* `context`: an object containing the context of the request, including access to [secrets](/docs/lambdas#secrets). This object is read-only. &nbsp;<AvailableSince since="1.64.0"/>

The [User API](/docs/apis/users) and [Registration API](/docs/apis/registrations) documentation describe the `user` and `registration` objects.

The `jwt` object holds the payload from the UserInfo endpoint. The payload can include registered OpenID Connect claims and custom claims from the Identity Provider.

FusionAuth passes the `id_token` to the lambda only when the IdP returns an `id_token` with a valid signature. The IdP returns an `id_token` when you request the `openid` scope.

FusionAuth verifies the signature in one of two ways:
* The IdP signs the token with the `client_secret` and an HMAC algorithm.
* The IdP signs the token with an asymmetric key pair. The IdP publishes the public key in a JSON Web Key Set (JWKS), and the `jwks_uri` in the `.well-known/openid-configuration` discovery document points to the JWKS. For FusionAuth to find the public key, configure the IdP with the Issuer so FusionAuth can read the discovery document. If you configure the Authorize, Token, and UserInfo endpoints by hand, FusionAuth doesn't discover the JWKS URI.

Before version `1.48.0`, FusionAuth passed the `id_token` only when the IdP signed the token with the `client_secret` and an HMAC algorithm.

The `tokens` object always holds the encoded `access_token`. When FusionAuth verifies the `id_token` signature, the `tokens` object also holds the encoded `id_token`. Use these tokens to call an external API with [Lambda HTTP Connect](/docs/lambdas/lambda-remote-api-calls).

## Assigning The Lambda

After you create the lambda, assign the lambda to one or more OpenID Connect identity providers.

Navigate to <Breadcrumb>Settings -> Identity Providers</Breadcrumb>. Select your existing OpenID Connect configuration. If you haven't configured OpenID Connect yet, click <Breadcrumb>Add provider</Breadcrumb> and select OpenID Connect.

## Modifying Email And Username Claims

The linking strategy decides which value FusionAuth requires to link a user. A strategy that links by email requires an email, and a strategy that links by username requires a username. FusionAuth reads each value from the UserInfo response first, then from the `id_token` when FusionAuth can verify the `id_token` signature. When neither has an email claim, the lambda can create a unique value. The email claim is `email` by default, and the username claim is `preferred_username`. To change the claim names, set `oauth2.emailClaim` and `oauth2.usernameClaim` with the [OpenID Connect Identity Provider API](/docs/apis/identity-providers/openid-connect).

<Aside type="note">
Available in FusionAuth `1.31.0` and later, and in versions `1.17.3` through `1.28.0`.
</Aside>

Use an email domain you control, so an attacker can't receive mail for the address. When the identity provider sends an `email_verified` claim of `false`, FusionAuth rejects a link by email, even when the lambda sets the email.

FusionAuth applies lambda changes to the email and username only at the first login, before a link exists. When the lambda changes the value that the linking strategy uses, and the new value matches an existing user, FusionAuth runs the lambda a second time with that user. After FusionAuth links the user, FusionAuth discards lambda changes to the email, the username, and the phone number.

When the linking strategy uses the username, FusionAuth ignores changes to the email. When the linking strategy uses the email, FusionAuth ignores changes to the username. FusionAuth ignores changes to the phone number for both strategies. Changes to the other claim could cause collisions if you change the linking strategy later.
