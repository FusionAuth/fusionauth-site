A new FusionAuth instance uses defaults that are convenient for development. Before you put an instance into production, work through the steps on this page. Each step links to the full reference for the setting it changes.

The first section applies to every instance, including FusionAuth Cloud. The second section applies only when you self-host, because FusionAuth Cloud manages that infrastructure for you. See [Who Secures What](/docs/cloud/cloud-vs-self-hosted#who-secures-what) for the split.

For a broader checklist to audit against, see the [OWASP Application Security Verification Standard](https://owasp.org/www-project-application-security-verification-standard/).

## Secure Every Instance

These steps change settings in the Admin UI, so they work the same on FusionAuth Cloud and self-hosted instances.

### Protect Admin Accounts

An admin account can change every setting and read every user, so protect these accounts first:

1. Confirm that the authenticator app method is enabled at <Breadcrumb>Tenants -> Your Tenant -> Multi-Factor</Breadcrumb>. It is enabled on the default Tenant and available on every plan.
1. Have each administrator [enable MFA on their account](/docs/lifecycle/authenticate-users/multi-factor-authentication#enable-mfa-for-a-user).
1. On the Enterprise plan, set the **On login policy** of the FusionAuth Application to `Required` at <Breadcrumb>Applications -> FusionAuth -> Multi-Factor</Breadcrumb>. This requires MFA for the Admin UI without requiring it for your other Applications.
1. Give each administrator only the [Admin UI roles](/docs/get-started/core-concepts/types/roles#admin-ui-roles) they need. For example, support staff need `user_support_manager`, not `admin`.

### Strengthen Passwords

Configure the password policy at <Breadcrumb>Tenants -> Your Tenant -> Password</Breadcrumb>:

1. Raise **Minimum length**. The default is `8`. [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html) recommends at least 15 characters when a password is the only factor. Length helps more than character-type rules, so you can leave those off.
1. Enable [breached password detection](/docs/operate/secure/breached-password-detection) on the Starter plan and above. It rejects passwords that appear in known breaches.
1. Configure [account lockout](/docs/lifecycle/authenticate-users/setting-up-user-account-lockout). FusionAuth counts failed logins by default, but doesn't lock an account until you select a **User action** under **Failed authentication settings**.

To avoid passwords altogether, offer [passkeys](/docs/lifecycle/authenticate-users/passkeys).

### Shorten Token and Session Lifetimes

A stolen token works until it expires, so keep lifetimes short. Configure these at the Tenant level, and override them per Application where needed:

1. Lower **JWT duration** at <Breadcrumb>Tenants -> Your Tenant -> JWT</Breadcrumb>. The default is `3600` seconds. Use the shortest value your applications handle well, such as 5 to 15 minutes.
1. Set **Refresh token usage** to `One-time use` in the same tab. Each refresh then returns a new refresh token and invalidates the old one, which the [OAuth 2.0 Security Best Current Practice](https://datatracker.ietf.org/doc/html/rfc9700#name-refresh-token-protection) recommends for public clients.
1. Lower **Refresh token duration** from the default of 30 days if users can sign in more often. Set **Refresh token expiration** to sliding window with a maximum lifetime to keep active users signed in up to a fixed limit.
1. Review **Session timeout** at <Breadcrumb>Tenants -> Your Tenant -> OAuth</Breadcrumb>. This is how long an [SSO session](/docs/lifecycle/authenticate-users/logout-session-management#fusionauth-sso) can be idle. The default is `3600` seconds.

See the [Tenant JWT settings](/docs/get-started/core-concepts/types/tenants#jwt) for every option.

### Require PKCE

PKCE stops an intercepted authorization code from being exchanged for tokens. For each Application, set **PKCE** to `Required` at <Breadcrumb>Applications -> Your Application -> OAuth</Breadcrumb>. The default is `Not required`.

If a server-side application can't send a code verifier, use `Not required when using client authentication` for it instead. See [RFC 7636](https://datatracker.ietf.org/doc/html/rfc7636) for how PKCE works.

### Restrict API Keys

An API Key with no endpoints selected can call every API, so create keys with only the access they need at <Breadcrumb>Settings -> API Keys</Breadcrumb>:

1. Select only the **Endpoints** and methods the key's consumer calls.
1. In a multi-tenant instance, select a **Tenant** to limit the key to that Tenant.
1. Set an **Expiration** for keys that have a limited lifetime.
1. Set **Retrievable** to `Not Retrievable` so the key value can't be read again after you create it.
1. On the Enterprise plan, add an **Access Control List** to limit the IP addresses that can use the key.

Store one unrestricted key in a secrets vault for emergencies, and don't use it day to day. See [API Key Permissions](/docs/apis/authentication#api-key-permissions) for details, and [Key Rotation](/docs/operate/secure/key-rotation) to rotate API Keys and signing keys.

### Monitor Security Events

Send login events to your logging or security monitoring system with a [webhook](/docs/extend/events-and-webhooks). Useful events include [`user.login.failed`](/docs/extend/events-and-webhooks/events/user/login/user-login-failed), [`user.password.breach`](/docs/extend/events-and-webhooks/events/user/password/user-password-breach), and on the Enterprise plan, [`user.login.suspicious`](/docs/extend/events-and-webhooks/events/user/login/user-login-suspicious).

When you enable these events at <Breadcrumb>Tenants -> Your Tenant -> Webhooks</Breadcrumb>, set **Transaction setting** to `No Webhooks are required to succeed`. Otherwise an outage in your monitoring system blocks logins. [Sign the webhook](/docs/extend/events-and-webhooks/signing) so your receiver can verify each event came from FusionAuth.

The [audit log](/docs/apis/audit-logs) records changes made in the Admin UI. Changes made directly with an API Key aren't recorded unless your code adds an entry with the Audit Log API.

### Limit What the Login Pages Reveal

Some hosted page responses reveal whether an account exists, such as the message for a locked account. FusionAuth already avoids this on the forgot password page. See [Account Enumeration](/docs/operate/secure/account-enumeration) to decide which responses to change.

## Secure a Self-Hosted Instance

When you self-host, you also secure the network, the database, and the search engine.

```mermaid title="Where the self-hosted controls apply. FusionAuth Cloud manages everything except the FusionAuth configuration."
graph TD
    client[Browser or app] -->|HTTPS| proxy["`**Reverse proxy**
    TLS, security headers,
    rate limits, Admin UI allowlist`"]
    proxy -->|Private network| fa["`**FusionAuth**
    Trusted proxies,
    production runtime mode`"]
    fa -->|TLS| db[(Database)]
    fa -->|Localhost or private network| search[(Search engine)]
```

### Put FusionAuth Behind a Proxy

Run FusionAuth behind a [reverse proxy](/docs/operate/deploy/proxy-setup), and use the proxy to:

1. Terminate TLS with TLS 1.2 or later, and redirect HTTP to HTTPS.
1. Add the [security headers](/docs/operate/deploy/proxy-setup#security-headers) that FusionAuth doesn't send.
1. [Restrict the Admin UI](/docs/operate/deploy/proxy-setup#restricting-the-admin-ui) to your administrators' networks.
1. Rate limit requests per IP address. FusionAuth's own [rate limits](/docs/operate/secure/advanced-threat-detection#customizable-rate-limiting) count actions per user, so they don't stop requests that never name a user.

Then [block direct access](/docs/operate/deploy/proxy-setup#locking-fusionauth-down) to FusionAuth on port `9011` from everywhere except the proxy.

### Trust Only Your Proxies

FusionAuth reads the client IP address from the `X-Forwarded-For` header. By default it trusts every proxy, so a client can forge the header to change the IP address used for IP ACLs and logs. At <Breadcrumb>Settings -> System -> Networking</Breadcrumb>, set **Trust policy** to `Only Configured` and list your proxy addresses. See [Networking Configuration](/docs/operate/secure/networking).

### Secure the Database and Search Engine

The database holds password hashes and personal data, and the search engine holds a copy of user data:

1. Encrypt the database connection with TLS. See **`database.url`** in the [configuration reference](/docs/reference/configuration) for an example.
1. Give FusionAuth its own database user, and restrict access to the database and its backups. See [Database Access](/docs/operate/secure#database-access).
1. Keep the search engine off public networks. A single-node install binds it to localhost by default. See [Required Ports](/docs/operate/secure#required-ports) for clusters.

### Protect Configuration and Secrets

1. Set **`fusionauth-app.runtime-mode`** to `production`. In the default `development` mode, FusionAuth shows the interactive Maintenance Mode pages to anyone who reaches the instance while the database needs setup or an update.
1. Keep database passwords and other secrets out of version control. Make the configuration file readable only by the user that runs FusionAuth, or inject secrets as environment variables from a secrets manager. See [Configuration Information](/docs/operate/secure#configuration-information).
1. If you use [Kickstart](/docs/get-started/download-and-install/development/kickstart), [reference secrets with environment variables](/docs/get-started/download-and-install/development/kickstart#using-environment-variables), and replace the API Key it creates once the instance is running.

Updates include security fixes. To hear about them, subscribe to the [release notes feed](/docs/releases.xml), and assign the `Security Officer` role to your account at [account.fusionauth.io](https://account.fusionauth.io) to join the security announcement list.
