Users can register [[passkeys]] and log in with them in the following ways:

* The FusionAuth [[hosted login pages]] run the browser side of each WebAuthn ceremony for you. A theme makes the pages match your application.
* The WebAuthn API lets your application run each ceremony on its own pages.

Passkeys on the user's device, such as Touch ID or Windows Hello, require a Licensed Community plan. Cross-platform authenticators, such as security keys, require an Enterprise plan.

## Use the Hosted Login Pages

The hosted login pages convert data between the FusionAuth APIs and the [WebAuthn JavaScript API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Authentication_API), and call the WebAuthn JavaScript API. The hosted login pages need no configuration beyond [Enable WebAuthn](#enable-webauthn).

The hosted login pages support the re-authentication workflow and the bootstrap workflow. You can change every page in both workflows with a theme, like any other hosted login page.

### Re-authentication

The re-authentication workflow speeds up repeated logins from the same device. FusionAuth prompts users to opt in when FusionAuth detects a compatible device. The next time the user logs in, FusionAuth shows a page that lists the user's passkeys on that device. The user clicks a passkey and completes the WebAuthn authentication ceremony.

#### Register a Re-authentication Passkey

After a successful login, FusionAuth sends the user to a passkey prompt when both of the following are true:

* The re-authentication workflow is enabled.
* The browser reports a suitable device through the [isUserVerifyingPlatformAuthenticatorAvailable()](https://developer.mozilla.org/en-US/docs/Web/API/PublicKeyCredential/isUserVerifyingPlatformAuthenticatorAvailable) JavaScript method.

<Screenshot url="/oauth2/authorize?client_id=e9fdb985-9173-4e01-9d73-ac2d60d1dc8e&response_type=code&redirect_uri=https%3A%2F%2Fexample.com&prompt=login" alt="The re-authentication prompt page asking users to register a passkey." id="passkeys-reauth-enable" />

The prompt lists the user's passkeys that meet the attachment and user verification requirements of the Tenant. The prompt also has a form to register a new passkey. The list has the following limits:

* A listed passkey can belong to an [[authenticator]] that isn't present, such as a removable security key.
* A listed passkey can belong to another browser. A passkey registered with a platform authenticator in one browser usually doesn't work in a different browser.
* Registration fails when the user registers a new passkey with an authenticator that already holds one of the user's passkeys.

The user can select a listed passkey and complete a WebAuthn authentication ceremony. Or the user can enter a display name and register a new passkey. Either way, FusionAuth marks the passkey for re-authentication. The next time FusionAuth would show a login page, FusionAuth shows the re-authentication page instead.

To skip the prompt, the user clicks <Breadcrumb>Not now</Breadcrumb>. When the user also selects **Don't ask me again on this device**, FusionAuth stops showing the prompt on that device.

#### Log In with a Re-authentication Passkey

When a user starts a login on the hosted login pages, FusionAuth checks whether the user has set up a passkey for this device. When FusionAuth finds one, FusionAuth shows the re-authentication page.

![The re-authentication page, listing the passkeys on the device.](/img/docs/lifecycle/authenticate-users/passwordless/reauth.png)

The page lists the passkeys on the device. Each passkey belongs to one account, so the user picks an account by picking a passkey. Clicking a passkey starts the WebAuthn authentication ceremony, and only the selected passkey can complete the ceremony. When the ceremony succeeds, FusionAuth logs the user in.

To use the normal login page instead, the user clicks <Breadcrumb>Return to the normal login</Breadcrumb>.

### Bootstrap Authentication

In the bootstrap workflow, the user starts the WebAuthn authentication ceremony by entering a username, email address, or phone number. The re-authentication workflow prompts users automatically, while the bootstrap workflow waits for the user to choose a passkey login. The user can complete the ceremony with any passkey whose authenticator meets the attachment and user verification requirements of the workflow.

#### Register a Bootstrap Passkey

When the re-authentication workflow is disabled, the login pages don't prompt users to add a passkey. Users can add passkeys through [self-service account management](/docs/users/account-management/), which requires a Starter plan. On a Licensed Community plan, register passkeys with the [WebAuthn API](#use-the-webauthn-api) instead.

<Screenshot url="/oauth2/authorize?client_id=e9fdb985-9173-4e01-9d73-ac2d60d1dc8e&response_type=code&redirect_uri=https%3A%2F%2Fexample.com&prompt=login" alt="The self-service passkeys management page." id="passkeys-self-service" />

The account page lists the user's passkeys, with a button to delete each passkey and a button to add a passkey. The account page registers passkeys with the broadest attachment and user verification settings. With an Enterprise plan, that includes cross-platform authenticators. Otherwise the account page accepts only platform authenticators.

A passkey on the account page doesn't always work with every enabled workflow. For example, when the user adds a security key but the bootstrap workflow accepts only platform authenticators, the security key appears in the list but can't complete a bootstrap login.

#### Log In with a Bootstrap Passkey

When the bootstrap workflow is enabled, the login page shows a <Breadcrumb>Fingerprint, device or key</Breadcrumb> button:

  <Highlight selector="[data-hl='webauthn-bootstrap-btn']" />
</Screenshot>

When the browser holds a re-authentication passkey, the login page also shows a <Breadcrumb>Return to passkey authentication</Breadcrumb> link above the other login methods. The link opens the re-authentication page.

Clicking <Breadcrumb>Fingerprint, device or key</Breadcrumb> opens the bootstrap login page:

## Prompt Users to Add a Passkey

When the re-authentication workflow is enabled, the hosted login pages already prompt users for a passkey after login. For more information, see [Register a Re-authentication Passkey](#register-a-re-authentication-passkey).

To prompt users from your own application instead:

<Steps>

1. In the browser, call [isUserVerifyingPlatformAuthenticatorAvailable()](https://developer.mozilla.org/en-US/docs/Web/API/PublicKeyCredential/isUserVerifyingPlatformAuthenticatorAvailable). When the method returns `false`, the device has no built-in authenticator, so skip the prompt. The hosted re-authentication prompt makes the same check.

   ```javascript
   const canPrompt = window.PublicKeyCredential &&
     await PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable();
   ```

1. On your server, retrieve the user's passkeys with the [Retrieve a Passkey API](/docs/apis/webauthn/retrieve-a-passkey). The API requires an API key with the `GET` permission on `/api/webauthn`:

   ```shell-session
   curl -H "Authorization: $API_KEY" \
     "https://auth.example.com/api/webauthn?userId=$USER_ID"
   ```

   When the user has no passkeys, FusionAuth returns `{"credentials": []}`. The list includes passkeys from every browser and device, including security keys. The API can't tell which passkeys work on the current device. A user with a passkey only in another browser still has a passkey in the list, so this check skips that user.

1. Skip the prompt when the user has dismissed the prompt before. To remember a dismissal across devices, store a flag in **`user.data`** with the [Update a User API](/docs/apis/users/update):

   ```shell-session
   curl -X PATCH -H "Authorization: $API_KEY" \
     -H "Content-Type: application/json" \
     "https://auth.example.com/api/user/$USER_ID" \
     -d '{"user": {"data": {"passkeyPromptDismissed": true}}}'
   ```

   The user's profile then has **`data.passkeyPromptDismissed`** set to `true`. To remember a dismissal on one device only, set a cookie instead.

1. Show the prompt. When the user accepts, add the passkey in one of the following ways:

   * Register the passkey with the WebAuthn API, and keep the user on your own pages. Set **`workflow`** to the workflow the passkey serves, such as `bootstrap`. For the steps, see [Register a Passkey](#register-a-passkey).
   * Send the user to `https://auth.example.com/account/webauthn/add?client_id=<clientId>`, the add passkey page of the self-service account pages. Set `<clientId>` to the client Id of your Application. The account pages require a Starter plan, a self-service form on the Application, and a user registered to the Application. After the user adds the passkey, FusionAuth shows the user's passkey list and doesn't return the user to your application. For more information, see [Add WebAuthn Passkey](/docs/users/account-management/add-webauthn).

</Steps>

To find every user without a passkey, call the Retrieve a Passkey API once per user. The [User Search API](/docs/apis/users/search) can't filter users by passkey.

## Use the WebAuthn API

The WebAuthn API lets you build every part of the login experience. The WebAuthn API also lets you track which passkeys work for re-authentication in your own way. For every WebAuthn API call, see the [WebAuthn API reference](/docs/apis/webauthn).

The `/api/webauthn/start` and `/api/webauthn/register/start` endpoints require an [API key](/docs/apis/authentication) with the `POST` permission on each endpoint. The endpoints that complete a ceremony don't require an API key.

The registration and authentication ceremonies follow the same steps:

1. Call FusionAuth to start the ceremony.
1. Convert the options in the FusionAuth response for the WebAuthn JavaScript API.
1. Call the [WebAuthn JavaScript API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Authentication_API) in the browser with the converted options.
1. Convert the authenticator response for transport over the network.
1. Send the converted response to FusionAuth to complete the ceremony.

### Register a Passkey

The registration ceremony creates a new passkey for a user.

#### Start the Registration

To start a registration, call the [`/api/webauthn/register/start`](/docs/apis/webauthn/start-a-webauthn-passkey-registration) endpoint:

```shell-session title="Start WebAuthn Registration API call"
API_KEY=...
REQUEST_PAYLOAD='{...}'
curl  -H "Content-type: application/json" -H "Authorization: $API_KEY" https://local.fusionauth.io/api/webauthn/register/start -d $REQUEST_PAYLOAD
```

#### Convert the Registration Options

FusionAuth returns some fields as base64url-encoded strings. Convert the following fields to JavaScript [ArrayBuffers](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/ArrayBuffer) when the fields are present, and leave the rest of the response unchanged:

* **options.challenge**
* **options.excludeCredentials\[x].id**
* **options.user.id**

For details on each field, see the [`/api/webauthn/register/start`](/docs/apis/webauthn/start-a-webauthn-passkey-registration) response body.

The following function converts a base64url-encoded string:

<ExtractedCode title="Function to convert a base64url-encoded string to an ArrayBuffer" lang="javascript" src="webauthn/base64url-to-buffer.snippet.base64url-to-buffer.js" />

The following snippet builds `creationOptions` for `navigator.credentials.create()` from `options`, the **options** field of the FusionAuth response:

```javascript title="Transform API response for WebAuthn JavaScript API"
const creationOptions = {
  // publicKey indicates this is for WebAuthn
  publicKey: {
    ...options,
    challenge: base64URLToBuffer(options.challenge),
    excludeCredentials: options.excludeCredentials?.map(c => {
      return {
        ...c,
        id: base64URLToBuffer(c.id)
      }
    }) ?? [],
    user: {
      ...options.user,
      id: base64URLToBuffer(options.user.id)
    }
  }
};
```

#### Call navigator.credentials.create()

Pass `creationOptions` to [navigator.credentials.create()](https://developer.mozilla.org/en-US/docs/Web/API/CredentialsContainer/create). The function returns a [Promise](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise) that resolves to a [PublicKeyCredential](https://developer.mozilla.org/en-US/docs/Web/API/PublicKeyCredential). For details, see the [WebAuthn specification](https://www.w3.org/TR/webauthn-2/).

#### Convert the Registration Response

Convert the following fields of the `PublicKeyCredential` from `ArrayBuffer`s to base64url-encoded strings when the fields are present, where **credential** is the `PublicKeyCredential`:

* **credential.response.attestationObject**
* **credential.response.clientDataJSON**

For details on each field, see the [`/api/webauthn/register/complete`](/docs/apis/webauthn/complete-a-webauthn-passkey-registration) request body.

The following function converts an `ArrayBuffer`:

<ExtractedCode lang="javascript" title="Function to convert an ArrayBuffer to a base64url-encoded string" src="webauthn/buffer-to-base64url.snippet.buffer-to-base64url.js" />

After `navigator.credentials.create()` succeeds, the **response** field holds an [AuthenticatorAttestationResponse](https://developer.mozilla.org/en-US/docs/Web/API/AuthenticatorAttestationResponse). Read the authenticator's transports and any client extension results from the `PublicKeyCredential` and the **response** field. The following snippet builds `transformedCredential`, the **credential** field of the `/api/webauthn/register/complete` request:

```javascript title="Transform WebAuthn JavaScript API response for FusionAuth API request"
const transformedCredential = {
  id: credential.id,
  response: {
    attestationObject: bufferToBase64URL(credential.response.attestationObject),
    clientDataJSON: bufferToBase64URL(credential.response.clientDataJSON)
  },
  type: credential.type,
  clientExtensionResults: credential.getClientExtensionResults(),
  transports: typeof credential.response.getTransports === 'undefined' ? [] : credential.response.getTransports()
};
```

#### Complete the Registration

To complete the registration, call the [`/api/webauthn/register/complete`](/docs/apis/webauthn/complete-a-webauthn-passkey-registration) endpoint:

```shell-session title="Complete WebAuthn Registration API call"

curl  -H "Content-type: application/json" https://local.fusionauth.io/api/webauthn/register/complete -d $REQUEST_PAYLOAD
```

### Authenticate with a Passkey

The authentication ceremony logs a user in with a passkey. To check that a user holds a passkey without logging the user in, see [Complete an Assertion](#complete-an-assertion).

Convert the following fields to `ArrayBuffer`s when the fields are present, and leave the rest of the response unchanged:

* **options.challenge**
* **options.allowCredentials\[x].id**

For details on each field, see the [`/api/webauthn/start`](/docs/apis/webauthn/start-a-webauthn-passkey-assertion-or-authentication) response body.

The following function converts a base64url-encoded string:

<ExtractedCode lang="javascript" title="Function to convert a base64url-encoded string to an `ArrayBuffer`" src="webauthn/base64url-to-buffer.snippet.base64url-to-buffer.js" />

The following snippet builds `requestOptions` for `navigator.credentials.get()` from `options`, the **options** field of the FusionAuth response:

```javascript title="Transform API response for WebAuthn JavaScript API"
const requestOptions = {
  // publicKey indicates this is for WebAuthn
  publicKey: {
    ...options,
    challenge: base64URLToBuffer(options.challenge),
    allowCredentials: options.allowCredentials.map(c => {
      return {
        ...c,
        id: base64URLToBuffer(c.id)
      }
    })
  }
};
```

#### Call navigator.credentials.get()

Pass `requestOptions` to [navigator.credentials.get()](https://developer.mozilla.org/en-US/docs/Web/API/CredentialsContainer/get). The function returns a [Promise](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise) that resolves to a [PublicKeyCredential](https://developer.mozilla.org/en-US/docs/Web/API/PublicKeyCredential). For details, see the [WebAuthn specification](https://www.w3.org/TR/webauthn-2/).

#### Convert the Authentication Response

Convert the following fields of the `PublicKeyCredential` from `ArrayBuffer`s to base64url-encoded strings when the fields are present, where **credential** is the `PublicKeyCredential`:

* **credential.response.authenticatorData**
* **credential.response.clientDataJSON**
* **credential.response.signature**
* **credential.response.userHandle**

For details on each field, see the [`/api/webauthn/login`](/docs/apis/webauthn/complete-a-webauthn-passkey-authentication) and [`/api/webauthn/assert`](/docs/apis/webauthn/complete-a-webauthn-passkey-assertion) request bodies.

The following function converts an `ArrayBuffer`:

<ExtractedCode title="Function to convert an ArrayBuffer to a base64url-encoded string" lang="javascript" src="webauthn/buffer-to-base64url.snippet.buffer-to-base64url.js" />

After `navigator.credentials.get()` succeeds, the **response** field holds an [AuthenticatorAssertionResponse](https://developer.mozilla.org/en-US/docs/Web/API/AuthenticatorAssertionResponse). Read any client extension results from the `PublicKeyCredential`. The following snippet builds `transformedCredential`, the **credential** field of the `/api/webauthn/login` or `/api/webauthn/assert` request:

```javascript title="Transform WebAuthn JavaScript API response for FusionAuth API request"
let userHandle = undefined;
if (credential.response.userHandle) {
  userHandle = bufferToBase64URL(credential.response.userHandle);
}
const transformedCredential = {
  id: credential.id,
  response: {
    authenticatorData: bufferToBase64URL(credential.response.authenticatorData),
    clientDataJSON: bufferToBase64URL(credential.response.clientDataJSON),
    signature: bufferToBase64URL(credential.response.signature),
    userHandle
  },
  type: credential.type,
  clientExtensionResults: credential.getClientExtensionResults()
};
```
