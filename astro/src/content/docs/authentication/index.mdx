FusionAuth logs users in with many methods. Start with the decision that shapes the rest of your integration: use the [hosted login pages or the Login API](#hosted-login-pages-or-the-login-api). Most apps use the [[hosted login pages]] with [OAuth and OpenID Connect](/docs/authentication/oauth).

Then add the login methods your users need:

* Passwordless login with [passkeys](/docs/authentication/passkeys) or [one-time passwords](/docs/authentication/one-time-passwords).
* A second factor with [multi-factor authentication](/docs/authentication/multi-factor-authentication).
* Login through Google, Apple, an enterprise directory, or another [identity provider](/docs/authentication/identity-providers).
* [Single sign-on](/docs/authentication/sessions/single-sign-on) across your applications.

To let other applications log users in through FusionAuth, see [Host a SAML v2 Identity Provider](/docs/authentication/act-as-an-idp/host-saml-idp), and the integration guides for [OpenID Connect](/docs/authentication/act-as-an-idp/oidc) and [SAML v2](/docs/authentication/act-as-an-idp/saml).

## Hosted Login Pages or the Login API

With the hosted login pages, your app redirects the browser to FusionAuth, and FusionAuth renders login, registration, MFA, and the other login steps. With the [Login API](/docs/authentication/login-api), your app renders every screen and calls FusionAuth behind the scenes. You can mix both, for example hosted login for the browser and the API for a custom step.

### Hosted Login Pages

Hosted login pages suit most apps. You customize the look with the [Simple Theme editor](/docs/theme/simple-theme-editor), or with [Apache FreeMarker templates](/docs/theme/advanced-themes) for full control. The browser has to redirect to FusionAuth.

![A diagram showing Apache FreeMarker side by side with FusionAuth's Simple Theme editor.](/img/articles/hosted-vs-api/simple-vs-freemarker.png)

<Table widths="1 1" headerRows={1}>
* * Pros
  * Cons
* * Managed by experts.
  * Look and feel customization uses Freemarker unless you use Simple Themes.
* * No sensitive credentials seen by your application.
  * Browser redirect is required.
* * Fully custom look and feel.
  * Mobile devices use the system browser, not native UX components. See the image below this chart for an example.
* * Handles multiple use cases (account creation, MFA prompting, etc.)
  * Does not leverage React or other common design systems. Might require additional work from your design team.
* * Includes single sign-on (SSO) between different apps.
  * Updates can be problematic unless you're using Simple Themes.
* * Localization support.
  * Limited workflow customization.
* * New workflows added regularly so you gain function without added development work.
  * &nbsp;
* * Doesn't exclude API usage. You can add custom logic such as redirects or requiring MFA for certain groups.
  * &nbsp;
</Table>

### Login API

The [[Login API]] gives you full control over every element of the login UI. That control comes with responsibilities, listed in the following table.

<Table widths="1 1" headerRows={1}>
* * Pros
  * Cons
* * A fully custom login experience, with support for embedded flows such as iframe, modals, overlays, and native application UI elements.
  * Must build your own UI for auth related cases, often requiring several API calls per use case.
* * Browser not required.
  * Doesn't follow OAuth or OIDC standards.
* * No redirection for the user.
  * Your application will see sensitive user credentials.
* * You are able to build custom workflows to suit your business needs. For example, asking for an email on one screen, a password on another and requesting MFA on a third.
  * You must handle all session management.
* * &nbsp;
  * You build it, you maintain it.
* * &nbsp;
  * You are responsible for implementing new FusionAuth functions when they are released.
* * &nbsp;
  * You must ensure that you handle every Login API status code correctly and securely.
* * &nbsp;
  * By default, the Login API requires an API key.
</Table>
