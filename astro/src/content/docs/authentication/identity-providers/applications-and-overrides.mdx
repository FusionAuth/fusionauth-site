## Identity Providers and Applications

You enable each Identity Provider for each Application separately, on the <Breadcrumb>Applications</Breadcrumb> tab of the Identity Provider. The following Google Identity Provider is enabled for the PiperChat Application, with **Create registration** turned on:

<Screenshot id="idp-google-applications" url="/admin/identity-provider/edit/Google/00000000-0000-0000-0000-f20000000133" alt="The Applications tab of a Google Identity Provider, enabled for the PiperChat Application with Create registration turned on.">
  <Highlight selector="[data-hl='idp-app-row']" />
</Screenshot>

When **Create registration** is on, a user doesn't need a registration before logging in through the Identity Provider. For example, a new user logs in to PiperChat with Google. When the user doesn't exist in FusionAuth, FusionAuth creates the user. FusionAuth then registers the user for PiperChat and assigns the default roles of the Application.

When **Create registration** is off, FusionAuth doesn't register users through the Identity Provider. A user without a Registration can still log in, but gets no authorization for the Application. An API login returns a `202` status code. To authorize the user, register the user for the Application before the user logs in with Google.

Self-service registration still applies when **Create registration** is off. When the Application has **Registration mode** set to `Create registration`, a hosted login through the Identity Provider creates the Registration. For more information, see [Registrations and Self-Service Registration](/docs/concepts/types/registrations#registrations-and-self-service-registration).

<Aside type="note">
FusionAuth can create a user during a login through an Identity Provider whether **Create registration** is on or off. The linking strategy decides whether FusionAuth creates the user. **Create registration** decides only whether FusionAuth registers the user, and so authorizes the user, for the Application. For more information, see [Linking Strategies](/docs/authentication/identity-providers/linking-strategies).
</Aside>

An enabled Identity Provider becomes an additional source of record (SoR) for users. When a user logs in to the Identity Provider, such as Google, the Identity Provider tells FusionAuth that the user exists and the credentials are valid. FusionAuth accepts the Identity Provider as a source of record, and creates a link, a user, or both, depending on the linking strategy. FusionAuth then checks **Create registration** to decide whether to register the user for the Application.

## CIMD Clients

<AvailableSince since="1.70.0" />

You can enable an Identity Provider for [CIMD clients](/docs/authentication/oauth/client-registration#client-id-metadata-documents). Each [CIMD domain](/docs/concepts/types/cimd-domains) appears in the <Breadcrumb>Applications</Breadcrumb> list with a `CIMD:` prefix, such as `CIMD: https://claude.ai`. A tenant-scoped Identity Provider lists only the [[CIMD]] domains in the Identity Provider's Tenant. When you enable an Identity Provider for a CIMD domain, every client that registers through the domain can use the Identity Provider.

Some options work differently for CIMD domains:

* **Create registration** is always off, because FusionAuth doesn't register users for CIMD clients.
* IdP-initiated SAML login isn't supported. The SAML v2 IdP Initiated Identity Provider doesn't list CIMD domains. On a SAML v2 Identity Provider with **Enable IdP initiated login** turned on, you can't enable a CIMD domain.

To configure CIMD domains with the [Identity Providers API](/docs/apis/identity-providers), use the CIMD domain Id as the key in **`identityProvider.applicationConfiguration`**.

## Overrides

<Aside type="version">
In FusionAuth `1.61.0` and later, you can create more than one instance of every Identity Provider type. A second instance of the Identity Provider type can replace Application overrides.
</Aside>

An override changes Identity Provider settings for one Application. For example, two Applications use the Apple Identity Provider. The first Application requests the `email name` scope, and the second Application requests only the `email` scope. Create the Apple Identity Provider with the scope `email name`, and enable the Identity Provider for both Applications. For the second Application, override **Scope** with `email`.

To override settings, expand <Breadcrumb>Overrides</Breadcrumb> in the Application's row on the <Breadcrumb>Applications</Breadcrumb> tab. You can override none, some, or all of the available settings. With the API, set the overrides in **`identityProvider.applicationConfiguration`**.

  <Highlight selector="[data-hl='idp-overrides']" />
</Screenshot>

The External JWT Identity Provider has no overrides, because you can create more than one External JWT Identity Provider.

<Breadcrumb>Overrides</Breadcrumb> doesn't offer every setting. **Linking strategy** is one setting that has no override. To use two values of such a setting, create a second instance of the Identity Provider, and enable each instance for a different Application.
