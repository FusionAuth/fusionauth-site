Identity Providers let users log in to FusionAuth through a third party. FusionAuth supports social Identity Providers, such as Facebook and Google, and enterprise Identity Providers, such as OpenID Connect and SAML v2.

To manage Identity Providers in the Admin UI, navigate to <Breadcrumb>Settings -> Identity Providers</Breadcrumb>. To manage Identity Providers through the API, see the [Identity Providers API](/docs/apis/identity-providers/).

## Enterprise Identity Providers

FusionAuth supports the following enterprise Identity Providers:

* [External JWT](/docs/authentication/identity-providers/external-jwt)
* [HYPR](/docs/authentication/identity-providers/enterprise/hypr)
* [OpenID Connect](/docs/authentication/identity-providers/overview-oidc)
* [SAML v2](/docs/authentication/identity-providers/overview-samlv2)
* [SAML v2 IdP Initiated](/docs/authentication/identity-providers/enterprise/samlv2-idp-initiated) (requires a paid plan)
* [Tenant Manager](/docs/users/tenant-manager), where Tenant administrators configure OpenID Connect and SAML v2 Identity Providers

To request an Identity Provider that FusionAuth doesn't support, search the open feature requests on [GitHub](https://github.com/FusionAuth/fusionauth-issues/issues). Vote or comment on an existing request, or open a new request.

## Account Security

When you configure an Identity Provider, you trust the Identity Provider to authenticate users. The Identity Provider controls MFA requirements and configuration, roles and groups, email and phone verification, and account identifiers.

<Aside type="caution">
Limit who can set up an Identity Provider. Your security is only as strong as the security of the platform that you federate to.
</Aside>

A malicious Identity Provider can harm your system. For example, a malicious Identity Provider can create accounts with email addresses that already exist in FusionAuth. A malicious user can then log in to the Identity Provider, return to FusionAuth, and access user data. The result is an account takeover.

To reduce the risk, consider the following strategies:

* Don't set up the Identity Provider.
* Enable the Identity Provider only for the Applications or Tenants that need the Identity Provider.
* Use a reconcile lambda to check that the email address or identifier from the Identity Provider is one you expect.
* Use the `Disabled` linking strategy, and manage links with the [Link API](/docs/apis/identity-providers/links). Your business logic then runs before or during linking. For example, your code can refuse links for a certain domain, or call another API to validate a link first.
* Use the [Login Validation lambda](/docs/lambdas/login/login-validation) to block a login.

## OAuth Scope Parameter

To request OAuth scopes on the FusionAuth access token, put the scopes in the `scope` parameter of the authorization request to FusionAuth.

The **Scope** field of the Identity Provider, when the Identity Provider has one, sets the `scope` parameter of the request to the Identity Provider.
