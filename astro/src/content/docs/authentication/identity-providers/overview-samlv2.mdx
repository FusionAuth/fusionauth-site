Add a login button that lets users authenticate through an external SAML v2 Identity Provider (IdP). FusionAuth acts as the SAML service provider.

<Aside type="note">
To use FusionAuth as a SAML v2 Identity Provider for other applications instead, see [Host a SAML v2 Identity Provider](/docs/authentication/act-as-an-idp/host-saml-idp).
</Aside>

Some SAML providers need specific configuration. The following guides cover those providers:

* [Configure SAML v2 for Active Directory Federation Services (ADFS)](/docs/authentication/identity-providers/enterprise/adfs)
* [Configure SAML v2 for Azure AD](/docs/authentication/identity-providers/enterprise/azure-ad-saml)
* [Configure SAML v2 for Okta](/docs/authentication/identity-providers/enterprise/okta-samlv2)

#### Form Fields

<APIBlock>
  <APIField name="Unique Id claim" optional>
    The name of the claim in the SAML response that contains the unique Id of the user. When you leave out the claim, FusionAuth uses the `NameID`.
  </APIField>
  <APIField name="Use NameId for email" optional>
    When enabled, FusionAuth reads the email address of the user from the `NameID` in the SAML response.
  </APIField>
  <APIField name="Email claim" optional>
    The name of the email claim in the SAML response.

    When **Use NameId for email** is enabled, the Admin UI hides this field, and the field isn't required.
  </APIField>
  <APIField name="Username claim" optional>
    The name of the username claim in the SAML response. FusionAuth never uses the `NameID` as the username. When you leave out the claim, the user has no username unless the reconcile lambda sets one. Set the claim when the **Linking strategy** links by username.
  </APIField>
  <APIField name="Use POST method" optional>
    When enabled, FusionAuth sends the authentication request with the HTTP POST binding. Otherwise, FusionAuth uses the default Redirect binding, which uses the HTTP GET method.
  </APIField>
  <APIField name="Sign requests" optional>
    When enabled, FusionAuth signs the authentication requests that FusionAuth sends to the Identity Provider.
  </APIField>
  <APIField name="Request signing key" optional>
    The key that signs the SAML request. This field is required when **Sign requests** is enabled. To create, manage, or import a key, navigate to <Breadcrumb>Settings -> Key Master</Breadcrumb>.
  </APIField>
  <APIField name="Canonicalization method" optional>
    The XML signature canonicalization method that FusionAuth uses to digest and sign the SAML request. This field is required when **Use POST method** and **Sign requests** are enabled.
  </APIField>
  <APIField name="Enable login hint" optional since="1.43.0">
    When enabled and the AuthN request uses HTTP redirect bindings, FusionAuth sends the username or email address to the IdP as a login hint, when available.
  </APIField>
  <APIField name="Login hint parameter name" optional since="1.43.0">
    The name of the parameter that passes the username or email address to the IdP as a login hint. FusionAuth sends the parameter when the AuthN request uses HTTP redirect bindings. This field is required when **Enable login hint** is enabled.
  </APIField>
  <APIField name="Destination assertion policy" optional since="1.43.0">
    The policy for the destination assertion on the SAML login request. The possible values are:

    * `Enabled`: FusionAuth verifies that the Destination attribute in the SAML response equals the FusionAuth [[ACS]] (Assertion Consumer Service) URL. `Enabled` is the default and the recommended setting.
    * `Disabled`: FusionAuth doesn't validate the Destination attribute. FusionAuth doesn't recommend this setting.
    * `Allow alternates`: FusionAuth verifies that the Destination attribute is either the FusionAuth ACS or one of the **Alternate destinations**. Use this setting with caution, to help migrate from a third-party IdP.
  </APIField>
  <APIField name="Alternate destinations" optional since="1.43.0">
    The URLs that FusionAuth accepts as SAML login destinations when **Destination assertion policy** is `Allow alternates`.
  </APIField>
  <APIField name="Require encrypted assertions" optional since="1.55.1">
    When enabled, FusionAuth requires encrypted assertions in SAML responses from the Identity Provider. FusionAuth rejects a SAML response that contains an unencrypted assertion.
  </APIField>
  <APIField name="Assertion decryption key" optional since="1.55.1">
    The key that decrypts SAML responses. This field is required when **Require encrypted assertions** is enabled. To create, manage, or import a key, navigate to <Breadcrumb>Settings -> Key Master</Breadcrumb>.

    The key must contain an RSA private key. Give the matching public key or certificate to the SAML Identity Provider, which uses the public key to encrypt assertions.
  </APIField>
</APIBlock>

## Signature Verification

FusionAuth verifies the signature on every SAML response from the Identity Provider. FusionAuth trusts only the keys in **Verification keys**. A certificate in Key Master that isn't in **Verification keys** can't verify a response.

FusionAuth chooses the verification key as follows:

* When the signature includes an X.509 certificate in the `KeyInfo` element, FusionAuth computes the SHA-1 thumbprint of the certificate. FusionAuth then verifies the signature with the key in **Verification keys** whose certificate has the same thumbprint. The order of the keys doesn't matter. When no key matches, FusionAuth rejects the response.
* When the signature doesn't include a certificate, FusionAuth verifies the signature with the default key. The default key is the key marked **Default** in the Admin UI, and the first key in **`verificationKeyIds`** in the API.

```mermaid title="FusionAuth chooses the key that verifies the signature on a SAML response from an external Identity Provider."
flowchart TD
    A[SAML response arrives] --> B{Does KeyInfo contain an X.509 certificate?}
    B -- Yes --> C{Does a certificate in Verification keys have the same SHA-1 thumbprint?}
    C -- Yes --> D[Verify the signature with the matching certificate]
    C -- No --> E[Reject the response]
    B -- No --> F[Verify the signature with the default key]
```

<Aside type="caution">
A verification key that contains only a public key, without a certificate, never matches the certificate in `KeyInfo`. A public key can verify a response only as the default key, and only when the signature doesn't include a certificate. When the Identity Provider gives you a certificate, import the certificate.
</Aside>

### Rotate Identity Provider Certificates

Many Identity Providers publish more than one signing certificate in their metadata. The extra certificates let service providers trust a new certificate before the Identity Provider starts to sign with the new certificate. To keep logins working during a certificate rotation:

1. Import each signing certificate from the metadata of the Identity Provider into Key Master. Navigate to <Breadcrumb>Settings -> Key Master</Breadcrumb>, and click <Breadcrumb>Import Certificate</Breadcrumb>.
1. Add each imported certificate to **Verification keys** on the Identity Provider.
1. Mark the certificate that the Identity Provider currently signs with as **Default**.
1. When the Identity Provider stops signing with the old certificate, remove the old certificate from **Verification keys**.

For more information, see [Key Master](/docs/security/tokens-and-keys/key-master).

## Integration Details

After you configure the Identity Provider, FusionAuth displays the values that your SAML v2 Identity Provider needs to trust FusionAuth as a [[relying party]]. To view the values, navigate to <Breadcrumb>Settings -> Identity Providers</Breadcrumb>, open the action menu next to your SAML provider, and click <Breadcrumb>View</Breadcrumb>.

Scroll to the <Breadcrumb>SAML v2 Integration details</Breadcrumb> section. The section contains the values you need to configure the integration with the SAML v2 IdP.

FusionAuth resolves the service provider EntityId from the `Issuer` value in the section. When you don't configure **`identityProvider.issuer`**, FusionAuth uses `<base_url>/samlv2/sp/<identityProviderId>`. When you configure **`identityProvider.issuer`**, FusionAuth uses your value.

FusionAuth expects the Audience value in the [[SAML assertion]] to match the same EntityId.

## CORS Configuration

To complete the login request, the SAML v2 Identity Provider sends an HTTP `POST` request to the callback URL in FusionAuth. To let the request through the [[CORS]] filter, navigate to <Breadcrumb>Settings -> System -> CORS</Breadcrumb>. Then add the origin of the SAML IdP as an **Allowed Origin** in the CORS configuration.

When your CORS configuration doesn't yet allow the login request, FusionAuth shows the following warning after you save the SAML v2 Identity Provider. For more information, see the [CORS Filter reference](/docs/security/clients/cors).

## Redirects

After a user logs in to the SAML IdP and returns to FusionAuth, FusionAuth can redirect the user to another URL. To set the redirect URL:

1. Choose the URL where the user arrives after login, such as `https://example.com/welcome`.
1. Add `https://example.com/welcome` to the **Authorized Redirect URLs** field in the Application configuration.
1. URL encode the URL. `https://example.com/welcome` becomes `https%3A%2F%2Fexample.com%2Fwelcome`.
1. Append the encoded URL to the ACS URL that you enter in the IdP as the `RelayState` parameter, such as `https://local.fusionauth.io/samlv2/acs?RelayState=https%3A%2F%2Fexample.com%2Fwelcome`.

When the request has no `RelayState` parameter, FusionAuth redirects the user to the first Authorized [[redirect URI]] in the OAuth configuration of the FusionAuth Application.

For more information, see [Integration Details](#integration-details).

### Redirects And Lambdas

A lambda that runs when a user logs in to FusionAuth with SAML can't change where FusionAuth sends the user. The lambda reads the SAML response and adds, modifies, or removes attributes on the User or Registration.

## Troubleshooting

<IdpManagedDomainsTroubleshooting idp_type_name="SAML" />

### Troubleshooting SAML Flows

To troubleshoot a SAML flow, enable **Enable debug logging**, and complete the SAML flow. Then navigate to <Breadcrumb>System -> Event Log</Breadcrumb>, and review the entries for configuration issues.

### Invalid Signature Errors

When FusionAuth can't verify the signature on a SAML response, the Event Log contains an error with the following message:

```plaintext
Invalid SAML v2.0 operation. The signature is invalid.
```

The error doesn't say which certificate the Identity Provider used. To find the certificate, enable **Enable debug logging**, and repeat the login. The debug entry in the Event Log contains the raw SAML response. Compare the `X509Certificate` value in the response with the certificates in **Verification keys**. When the certificate isn't in **Verification keys**, import the certificate and add the certificate to **Verification keys**. For more information, see [Signature Verification](#signature-verification).
