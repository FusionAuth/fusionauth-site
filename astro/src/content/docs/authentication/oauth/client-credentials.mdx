The Client Credentials grant lets one service get an access token to call another service, with no user involved. The grant runs between two [[Entity::Entities]] instead of an Application. To set up the Entities, see [Configure Entities](#configure-entities).

## Configure Entities

Two Entities take part in a Client Credentials grant. The recipient Entity requests the access token. The target Entity receives requests with the access token and controls access to itself. To learn more about Entities, see [Entity Management](/docs/concepts/types/entity-management).

For example, a todo API sends email reminders through an email API. The todo API is the recipient Entity, because the todo API receives permissions to call the email API. The email API is the target Entity, because the email API checks the token. To set up the relationship:

1. Create an API [[Entity Type]] with the permissions `read` and `write`.
1. Create a todo API Entity and an email API Entity with the API Entity Type.
1. Grant the todo API `read` permission on the email API.

You set up the relationship once. After that, the todo API runs the Client Credentials grant whenever the todo API needs to call the email API.

You can configure Entities and Grants in the Admin UI or with the API. You can set the **Client Id** and **Client secret** of an Entity, or let FusionAuth generate the values. To create an Entity, navigate to <Breadcrumb>Entity Management -> Entities</Breadcrumb> and click <IconButton icon="add" />:

To add a Grant with the API, send the recipient Entity Id and the permissions to the [Entity Grants API](/docs/apis/entities/grants):

```shell title="Example Grant Request"
API_KEY=...
TARGET_ENTITY_ID=e13365f1-a270-493e-bd1b-3d239d753d53
RECIPIENT_ENTITY_ID=2934f41f-d277-4a32-b0d5-16e47dad9721

curl \
  -XPOST \
  -H "content-type: application/json" \
  -H "Authorization: $API_KEY"  \
  'https://local.fusionauth.io/api/entity/'$TARGET_ENTITY_ID'/grant' -d'
{
  "grant": {
    "recipientEntityId": "'$RECIPIENT_ENTITY_ID'",
    "permissions" : ["read"]
  }
}
'
```

## Exchange Credentials for an Access Token

Send the Client Id and the client secret of the recipient Entity to the `/oauth2/token` endpoint, with **`grant_type`** set to `client_credentials`. The example sends the credentials in an `Authorization: Basic` header, and adds line breaks for readability.

```plaintext title="Example HTTP Request"
POST /oauth2/token HTTP/1.1
Host: piedpiper.fusionauth.io
Authorization: Basic MDkyZGJkZWQtMzBhZi00MTQ5LTljNjEtYjU3OGYyYzcyZjU5OitmY1hldDlJdTJrUWk2MXlXRDlUdTRSZVoxMTNQNnlFQWtyMzJ2NldLT1E9
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
    &scope=target-entity%3Ae13365f1-a270-493e-bd1b-3d239d753d53%3Aread
```

## Client Credentials Scopes

The **`scope`** parameter names the target Entities and the permissions to request. Separate multiple values with spaces. Each value has the following format:

```plaintext
target-entity:entity_id:permission
```

The `entity_id` is the Id of the target Entity and is required. The `permission` is an optional comma-separated list of permissions.

To request every permission the recipient has on a target Entity, name only the target Entity:

<ClientCredentialsScopesSingleEntity />

To request permissions on several target Entities, list several values:

<ClientCredentialsScopesMultipleEntities />

FusionAuth checks the requested permissions against the permissions granted to the recipient Entity. When the recipient has every requested permission, FusionAuth returns an **`access_token`**.

When you leave out **`scope`**, FusionAuth still returns an access token for an authorized request. The access token then has no **`aud`** or **`permissions`** claim.
