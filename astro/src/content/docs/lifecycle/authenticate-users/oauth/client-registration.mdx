Before an OAuth client can request tokens, the authorization server needs a record of it, including which redirect URLs the client may use. That record is the client's registration.

FusionAuth supports two ways to register a client:

* Static registration, where you create an [Application](/docs/get-started/core-concepts/types/applications) for the client ahead of time.
* Client ID Metadata Documents (CIMD), where the client describes itself in a document it hosts, and FusionAuth registers it the first time it shows up.

## Static Registration

With static registration, you create an Application in FusionAuth for each client. The Application Id becomes the client's `client_id`. You configure everything else on the Application: redirect URLs, enabled grants, client authentication, roles, and scopes.

Use static registration when you know your clients in advance, such as your own apps and services.

Someone has to create the Application before the client can log in. That doesn't work for software you don't control and can't predict, like an AI chat app connecting to your MCP server on behalf of a user.

With CIMD, the `client_id` is an HTTPS URL, such as `https://chatgpt.com/oauth/client.json`. The client hosts a JSON document at that URL describing itself, including its name and redirect URIs. CIMD is defined in [draft-ietf-oauth-client-id-metadata-document](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/), and the [MCP authorization spec](https://modelcontextprotocol.io/specification/draft/basic/authorization) uses it for client registration.

You don't register CIMD clients one at a time. Instead, you tell FusionAuth which origins to trust by creating a [CIMD domain](/docs/get-started/core-concepts/types/cimd-domains) for each one, for example `https://chatgpt.com`. You can configure scopes, consent, resource URIs, and lambdas for each domain.

### How A CIMD Client Gets Registered

1. The client starts the Authorization Code grant, using its document URL as the `client_id`. The request must go to the Tenant's endpoints, which end with the Tenant Id, such as `https://<host>/oauth2/authorize/<tenantId>`, and include exactly one [`resource` parameter](https://datatracker.ietf.org/doc/html/rfc8707), such as the URL of your MCP server.
1. FusionAuth checks that the URL matches a CIMD domain in the Tenant. If nothing matches, the request fails.
1. The user logs in.
1. FusionAuth fetches the document, validates it, and registers the client. If the domain has a registration lambda, the lambda can reject the client or change its registration.
1. The user consents to the requested scopes. CIMD clients are always treated as third-party clients, so FusionAuth always asks for consent at least once.
1. FusionAuth redirects back to the client with an authorization code, and the client exchanges it for tokens.

The `resource` must be one of the domain's **Authorized resource URIs**, or FusionAuth rejects the request with `invalid_target`. The `aud` claim of both the access token and the Id token contains two values: the client's `client_id` URL and the `resource`.

FusionAuth caches the document. Until the cached copy expires, later logins from the same client reuse the registration without fetching the document again. The domain's cache settings control how long that is, as described in [CIMD Registration Caching And Lifecycle](/docs/lifecycle/authenticate-users/oauth/cimd-registration-lifecycle). After the cached copy expires, the next login fetches the document again. Access and refresh tokens the client already holds keep working after the cached copy expires.

### Removing A CIMD Client

FusionAuth has no admin UI for removing a single CIMD client. There are three ways to remove access:

* Delete the client's registration with the [Delete a CIMD Client Registration API](/docs/apis/cimd-client-registrations/delete-a-cimd-client-registration). FusionAuth deletes the registration and its refresh tokens immediately. To find the registration Id, [search for the registration](/docs/apis/cimd-client-registrations/search-for-cimd-client-registrations) by its `client_id` URL.
* Set `decision` to `REVOKE` in the domain's registration lambda. FusionAuth deletes the client's registration and refresh tokens the next time the lambda runs for that client. The lambda runs when a user logs in after the client's cached document expires, or when the client requests a `resource` it hasn't used before.
* Delete the CIMD domain. This removes every client registered through the domain, along with their refresh tokens.

Deleting a registration doesn't block the client. The next time a user logs in with that client, FusionAuth registers it again. To keep a client out, also set `decision` to `DENY` for it in the registration lambda. A `DENY` decision on its own blocks new logins but leaves existing refresh tokens working.

### Monitoring CIMD Clients

To see which clients have registered, use the [Search for CIMD Client Registrations API](/docs/apis/cimd-client-registrations/search-for-cimd-client-registrations). Each registration shows the client's metadata, the scope decisions for each `resource` it has used, and whether its cached document is `Active`, in its `Grace` period, or `Expired`.

FusionAuth sends a [CIMD Registration Success](/docs/extend/events-and-webhooks/events/cimd/cimd-registration-success) event when it registers a client or updates a registration, and a [CIMD Registration Failed](/docs/extend/events-and-webhooks/events/cimd/cimd-registration-failed) event when it can't. Every failure also writes an Error entry to the Event Log. With **Enable debug logging** on the CIMD domain, successes write a Debug entry as well.

Logins through a CIMD client appear in login records and login reports under the CIMD domain's Id as the `applicationId`, even though the user has no registration for an Application with that Id. The [User Login Success](/docs/extend/events-and-webhooks/events/user/login/user-login-success) and [User Login Failed](/docs/extend/events-and-webhooks/events/user/login/user-login-failed) events work differently: they leave out `applicationId` and include the CIMD domain's Id as `cimdDomainId`.

### What CIMD Clients Can't Do

CIMD clients are public clients. They authenticate with PKCE instead of a client secret, and they can only use the `authorization_code` and `refresh_token` grants. See [Fixed OAuth Behavior](/docs/get-started/core-concepts/types/cimd-domains#fixed-oauth-behavior) for the full list of restrictions.

FusionAuth reads only `client_id`, `client_name`, `client_uri`, and `redirect_uris` from the document, and ignores every other field. A `scope` value in the document has no effect, so a CIMD client can only request the scopes enabled on its domain. FusionAuth also doesn't fetch `logo_uri`.

A CIMD client's access token can't authenticate the FusionAuth APIs that accept a user's JWT in place of an API key, such as the [Login API](/docs/apis/login), the [JWT](/docs/apis/jwt/issue-a-jwt) issue and refresh APIs, the [Change Password API](/docs/apis/users/change-password), and the two-factor APIs. Use the token with your own resource server, the [Userinfo](/docs/apis/oauth/userinfo) endpoint, or the [Introspect](/docs/apis/oauth/introspect) endpoint instead.

FusionAuth recognizes a CIMD client's token by its `aud` claim, which is always exactly `["<client_id URL>", "<resource>"]`. Don't change `aud` in a JWT populate lambda for a CIMD domain, because FusionAuth won't recognize the token as a CIMD token.

## Dynamic Client Registration

[Dynamic Client Registration](https://datatracker.ietf.org/doc/html/rfc7591) (DCR) is an older way to solve the same problem. Under DCR, the client calls a registration endpoint on the authorization server, and the server creates and stores a new client record for every caller. FusionAuth doesn't support DCR; you can follow [GitHub issue #1125](https://github.com/FusionAuth/fusionauth-issues/issues/1125) for updates. CIMD covers the MCP use case with less stored state, since the client's metadata stays on the client's own server.

## Choosing An Approach

| | Static registration | CIMD |
|---|---|---|
| Who registers the client | You, before the client logs in | FusionAuth, the first time the client logs in |
| `client_id` | The Application Id | The URL of the client's metadata document |
| Where the client's metadata lives | The Application | The client's document, cached by FusionAuth |
| What you configure | One Application per client | One CIMD domain per trusted origin |
| Client authentication | Client secret or none, with or without PKCE | None. PKCE is required |
| Grants | Any grant FusionAuth supports | `authorization_code` and `refresh_token` |
| Consent | Configurable, including skipping it for first-party apps | Always prompts at least once |
| Removing access | Delete or deactivate the Application | Delete the CIMD domain, or revoke the client with a registration lambda |

Use static registration for clients you know about. Use CIMD when clients you don't know in advance need to log in, such as MCP clients like ChatGPT and claude.ai connecting to your MCP server.
