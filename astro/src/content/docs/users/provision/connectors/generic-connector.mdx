A Generic Connector authenticates users against, or migrates users from, any user data source that FusionAuth can reach over HTTP or HTTPS.

## Configuration

<Screenshot id="migration-generic-connector-add" url="/admin/connector/add/Generic" crop="[data-migration-window]" cropPadding={0} chrome={true} alt="The Generic Connector creation page." />

### Form Fields

<APIBlock>
  <APIField name="Id" optional>
    An optional UUID. When you omit the Id, FusionAuth generates a unique Id.
  </APIField>
  <APIField name="Name" required>
    A unique name for the Connector. FusionAuth uses the name for display only, and you can change the name later.
  </APIField>
  <APIField name="Authentication URL" required>
    The fully qualified URL of your API endpoint. To authenticate a user, the Connector sends an HTTP POST request to this URL. The endpoint returns the same format as the [Login API](/docs/apis/login). For the status codes that FusionAuth accepts from the endpoint, see [Response](#response).
  </APIField>
  <APIField name="Connect timeout" required>
    The connect timeout for the POST request, in milliseconds.
  </APIField>
  <APIField name="Read timeout" required>
    The read timeout for the POST request, in milliseconds.
  </APIField>
  <APIField name="Enable debug logging" optional>
    When enabled, FusionAuth writes Event Log entries that help you debug integration errors. To view the entries, navigate to <Breadcrumb>System -> Event Log</Breadcrumb>.
  </APIField>
</APIBlock>

## Using the Generic Connector

To use a Generic Connector:

<Steps>

1. Build an API endpoint in your application that returns your user data. For the formats, see [Request](#request) and [Response](#response).
1. Configure the Connector in <Breadcrumb>Settings -> Connectors</Breadcrumb>, including the endpoint security.
1. Add a Connector policy in <Breadcrumb>Tenants -> Your Tenant -> Connectors</Breadcrumb>. The policy sets the domains that the Connector applies to.

</Steps>

### Request

FusionAuth sends the request to your API endpoint as JSON:

<JSON title="Example Request JSON" src="login/request.json" />

Your application looks up the user, checks the credentials, and returns a response.

### Response

When your API finds and authenticates the user, return a FusionAuth `user` object with status code `200`. You can return any attribute of the user object, including nested objects such as application registrations with roles. The response must include the required fields. For the required fields, see [Connectors](/docs/users/provision/connectors#required-fields).

When your API can't authenticate the user, return a `404`. FusionAuth accepts no other status codes from your API.

<Aside type="caution">
Return a FusionAuth-compatible UUID in **`user.id`**, whether or not the Connector migrates the user. When the Connector authenticates users without migrating the users, return the same **`user.id`** at every login.

For the errors that a non-UUID value causes, see [Response Parsing Errors](#response-parsing-errors).
</Aside>

### Response Parsing Errors

FusionAuth reads the response into a FusionAuth User object. When a field in the response has the wrong type or format, FusionAuth can't read the response, and the Login API returns a `404`. FusionAuth also writes an error to <Breadcrumb>System -> Event Log</Breadcrumb>, even when **Enable debug logging** is off.

The error says that FusionAuth failed to parse the HTTP response as JSON, even when the response body is valid JSON. The `Cause` part of the error names the field that failed and the type that FusionAuth expected. For example, an OIDC-style identifier in **`user.id`** produces the following error:

```plaintext
com.inversoft.rest.JSONException : Message: Failed to parse the HTTP response as JSON. Actual HTTP response body:
{"user":{"id":"auth0|5f1b2c3d4e","email":"richard@piedpiper.com","fullName":"Richard Hendricks"}}
Cause: com.fasterxml.jackson.databind.exc.InvalidFormatException
Message: Cannot deserialize value of type `java.util.UUID` from String "auth0|5f1b2c3d4e": UUID has to be represented by standard 36-char representation
 at [Source: REDACTED (`StreamReadFeature.INCLUDE_SOURCE_IN_LOCATION` disabled); line: 1, column: 15] (through reference chain: io.fusionauth.domain.api.LoginResponse["user"]->io.fusionauth.domain.User["id"])
```

The following values cause this error:

* A value other than a [UUID](/docs/apis/data-types#uuids) in an Id field, such as **`user.id`** or **`user.registrations[].applicationId`**.
* A date in **`user.birthDate`** in a format other than `YYYY-MM-DD`.
* A date string in an [instant](/docs/apis/data-types#instants) field, such as **`user.insertInstant`**. Instants are numbers of milliseconds.
* A value other than an object in **`user.data`**.

When the response has no **`user.id`**, FusionAuth discards the user, and the Login API returns a `404`. FusionAuth logs the reason only when **Enable debug logging** is on.

For the type of each field, see the [User response body](/docs/apis/users/retrieve#response-body).

## Performance Considerations

Each login through an enabled Connector waits for the Connector's response, so keep the Connector's latency low.

Set timeouts under one second. A longer timeout can starve FusionAuth of resources, because slow requests hold resources longer.

The following sections describe ways to improve the performance of your Generic Connector.

### Network Connection

The connection from the Connector to your API endpoint has the following phases:

1. FusionAuth connects to the API endpoint.
1. FusionAuth reads the first byte from the connection.
1. The API endpoint completes and returns the response.

**Connect timeout** limits the first phase. When the connect timeout expires before FusionAuth establishes the connection, the login fails. **Read timeout** limits the second phase. When the read timeout expires before data is available to read, the login fails. The default timeouts usually work. Tune the timeouts when your server has resource contention.

Neither timeout limits the third phase. After the API endpoint starts writing the response, the HTTP request can take as long as the endpoint needs. When the endpoint doesn't end the HTTP response correctly, or takes too long to process the login request, FusionAuth can have problems under load.

To avoid these problems, write the login response and close the connection as quickly as possible. Give the API endpoint enough resources. Return the correct status code for each response, so FusionAuth handles the response correctly.

### Add Database Indices

When your API endpoint queries a database to authenticate users, check the queries with database tooling such as `explain plan`. Add the indices that the queries need.

### Disable Logging

Turn on **Enable debug logging** during development to troubleshoot the Connector. In production, turn on debug logging only while you troubleshoot. Debug logging writes entries to <Breadcrumb>System -> Event Log</Breadcrumb>, and each entry adds load to the database.

### Perform Optional Actions Out of Band

Your API endpoint might run other tasks after a successful login, such as calling APIs or sending messages. When a task doesn't affect the authentication result, run the task after the endpoint sends the response to FusionAuth. For example, store the task data in a queue, and process the queue later in a separate process.

### Load Test

Load test your Connector in a staging environment with the [Login API](/docs/apis/login). Configure the tenant to use your Connector, and create users in your system. Then use a load testing tool to send repeated login requests to FusionAuth. For more information, see [Load Test](/docs/deploy/test/load-test).
