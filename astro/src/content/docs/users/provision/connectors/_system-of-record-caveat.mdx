
You can use this Connector as either a source of authentication or to migrate your users. In the former case, the {props.system_of_record} remains the system of record (where the canonical user data exists). In the latter, the user is moved over once they have authenticated successfully one time, and FusionAuth becomes the system of record.

As [documented](/docs/users/provision/connectors/), there are a number of differences between these two choices. However, one difference is worth emphasizing. 

When you are not migrating the user and therefore using the {props.system_of_record} as the system of record, the following user attributes will reset every time the user authenticates:

* Group memberships
* Application registrations
* [[Multi-Factor Authentication::Multi-factor authentication]] methods and recovery codes

If, for instance, you were to register such a user for an application using the FusionAuth API or the Admin UI, the next time they authenticated, they would not be registered for that application.

Since FusionAuth is not the system of record, the {props.system_of_record} is the authoritative data source.

<Aside type="danger" title="FusionAuth deletes the MFA methods of Connector users at login">
When the Connector policy doesn't migrate users, FusionAuth doesn't keep the multi-factor authentication methods that users set up in FusionAuth. Each login replaces the user's methods with the methods in the Connector response. FusionAuth replaces the methods before the multi-factor authentication check, so the login completes without a challenge. For example, a user who sets up an authenticator app gets no challenge on the next login, and FusionAuth deletes the authenticator app method.

To use FusionAuth multi-factor authentication with Connector users, turn on **Migrate user** in the Connector policy. FusionAuth then keeps the methods and challenges the user on each login.
</Aside>
