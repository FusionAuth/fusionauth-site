FusionAuth uses a [[Search Engine::search engine]] to find Users and Entities in the Admin UI, the User Search API, and the Entity Search API. FusionAuth supports the following search engines:

* The database search engine runs inside FusionAuth and needs no other service.
* The Elasticsearch search engine connects to an OpenSearch or Elasticsearch cluster that you run. Despite the name, the Elasticsearch search engine works the same way with OpenSearch.

A search engine service is optional. Login, registration, and every other feature that doesn't search for Users or Entities work the same with either engine. FusionAuth Cloud deployments use the Elasticsearch search engine.

## Compare the Search Engines

| Feature | Database | Elasticsearch |
|---|---|---|
| Extra service to run | None | OpenSearch or Elasticsearch |
| User and Entity search by Id | Yes | Yes |
| Search by `queryString` | Single terms in a few fields | Full query string syntax on any indexed field |
| Search by `query` (Elasticsearch query DSL) | No | Yes |
| Search custom **`data`** fields | No | Yes |
| Search across Registrations, Group memberships, and Entity grants | No | Yes |
| Advanced search in the Admin UI | No | Yes |
| [Bulk Delete Users API](/docs/apis/users/bulk-delete) | **`userIds`** and single-term **`queryString`** | All parameters |
| [SCIM](/docs/users/provision/scim) list Users with a **`filter`** | No | Yes |
| Page past 10,000 results | Yes | Yes, with **`nextResults`** tokens |
| Search results after a User changes | Immediate | After an index refresh, usually about one second |

Choose the database search engine for development, embedded installs, and installs that find Users by Id, email address, or name. With a large number of Users, load test the database search engine with your typical searches, because FusionAuth doesn't test that case. Provision the database with enough resources for search.

Choose the Elasticsearch search engine when you need any feature in the Elasticsearch column, or when you search a large number of Users often. For a new install, use OpenSearch `2.x`.

## Default Search Engine

The search engine depends on how you install FusionAuth:

* The [Docker install](/docs/get-started/install) uses the Elasticsearch search engine, and runs OpenSearch in a container.
* The `fusionauth/fusionauth-app` Docker image, without a `SEARCH_TYPE` environment variable, uses the database search engine.
* The FusionAuth App package and the [Fast Path install](/docs/deploy/production/install/fusionauth-app) use the database search engine.
* The FusionAuth Search package sets the Elasticsearch search engine, and runs Elasticsearch on the same server.

To see the search engine an instance uses, navigate to <Breadcrumb>System -> About</Breadcrumb> in the Admin UI. The **Search** row shows `Database`, or the name and version of OpenSearch or Elasticsearch, such as `OpenSearch 2.19.8`.

## Database Search Engine

The database search engine matches a single term against the following User fields:

* `firstName`
* `lastName`
* `fullName`
* `email`
* `phoneNumber` <AvailableSince since="1.59.0" />
* `username`

A search matches part of a field, without regard to case. Add a `*` wildcard to match any characters, including none: `*piedpiper` matches `piedpiper` and `thepiedpiper`. You can put the wildcard anywhere in the term. The database search engine doesn't support regular expressions, ranges, or compound queries. For the Entity fields the engine matches, see the [Entity Search API](/docs/apis/entities/entities#search-for-entities).

## Elasticsearch Search Engine

The Elasticsearch search engine keeps an index of Users and Entities in OpenSearch or Elasticsearch. FusionAuth writes to the index whenever a User or an Entity changes. FusionAuth indexes the following data:

* Users, with Registrations, Group memberships, and the **`user.data`** and **`registration.data`** fields. For the field list, see [Indexed User Fields](/docs/users/search/user-fields).
* Entities, with grants and the **`entity.data`** field. For the field list, see [Indexed Entity Fields](/docs/users/search/entity-fields).

With the index, you can search any indexed field with the full Elasticsearch query string syntax and query DSL. For examples, see [Search Users With OpenSearch or Elasticsearch](/docs/users/search/user-search-with-elasticsearch).

### What Uses the Search Engine

With the Elasticsearch search engine, the following features read from the search engine:

* The [User Search API](/docs/apis/users/search) and the [Entity Search API](/docs/apis/entities/entities#search-for-entities), with **`queryString`**, **`query`**, or **`nextResults`**. A search with **`ids`** reads from the database.
* The [Bulk Delete Users API](/docs/apis/users/bulk-delete), with **`queryString`** or **`query`**.
* SCIM requests that list Users with a **`filter`**.
* User and Entity search in the Admin UI.

The following changes write to the search engine:

* Creating, updating, and deleting Users, including through the [Import Users API](/docs/apis/users/import).
* Creating, updating, verifying, and deleting Registrations.
* Adding Users to Groups and removing Users from Groups.
* Creating, updating, and deleting Entities.
* Logins, which update the last login time of the User. FusionAuth writes login times in batches in the background.

Login, passwordless login, and retrieving a User or an Entity by Id don't read from the search engine.

### When the Search Engine Is Unavailable

When OpenSearch or Elasticsearch is down, FusionAuth keeps running, and users can still log in. Other requests behave as follows:

| Request | Result while the search engine is down |
|---|---|
| Login and passwordless login | Succeeds. |
| Retrieve a User or an Entity, or search with **`ids`** | Succeeds. |
| Search with **`queryString`** or **`query`**, or Bulk Delete Users | Fails with a `503` response. |
| Create or update a User, or create a Registration | Succeeds, but the change doesn't reach the index. |
| Delete a User, or add a User to a Group | Fails with a `503` response. FusionAuth makes no change. |
| Create, update, or delete an Entity | Fails with a `503` response. FusionAuth makes no change. |

A failed request returns the `[SearchEngineUnavailableException]` error code. After the search engine recovers, searches miss the changes that succeeded during the outage. To bring the index up to date, [reindex](#reindex).

A search engine that accepts connections but doesn't respond causes longer delays than one that is down. In testing with an unresponsive OpenSearch node, searches returned the `503` response after 30 seconds, a User update took 60 seconds, and the [System Status API](/docs/apis/system/retrieve-system-status) took 30 seconds. When User API calls slow down, check the health of the search engine cluster.

### Index Delay

The index is eventually consistent. After a User changes, the change appears in search results once the search engine refreshes the index, usually after about one second. For more information, see [Limitations](/docs/users/search/user-search-with-elasticsearch#limitations).

To make changes visible to search right away, for example in tests, call the [Flush the Search Engine API](/docs/apis/users/flush-search).

## Pagination

Both search engines page through results with **`startRow`** and **`numberOfResults`**. The Elasticsearch search engine also returns a **`nextResults`** token, which pages past the first 10,000 results. For more information, see [Pagination](/docs/users/search/user-search-with-elasticsearch#pagination) and [Extended Pagination](/docs/users/search/user-search-with-elasticsearch#extended-pagination).
