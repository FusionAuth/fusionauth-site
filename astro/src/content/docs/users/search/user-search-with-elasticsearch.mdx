This guide shows how to search for Users with the Elasticsearch search engine. The Elasticsearch search engine works the same way with OpenSearch and Elasticsearch, so every example on this page works with both. Entity searches use the same parameters. For the Entity fields, see [Indexed Entity Fields](/docs/users/search/entity-fields).

The examples use curl. To run the same searches from your application, use a [client library](/docs/sdks/).

## Prerequisites

* FusionAuth configured with the Elasticsearch search engine. To check the engine, navigate to <Breadcrumb>System -> About</Breadcrumb> in the Admin UI. The **Search** row shows `OpenSearch` or `Elasticsearch` with the Elasticsearch search engine. To set up the engine, see [Install a Search Engine](/docs/deploy/production/install/search).
* An API key with access to the `/api/user/search` endpoint.

With the database search engine, the User Search API accepts only simple terms. For the differences between the engines, see [Search Engines](/docs/users/search).

## Search Parameters

A search request uses one of the following parameters. The parameters are mutually exclusive.

| Parameter     | Uses the search engine | Use for |
|---------------|------------------------|---------|
| `ids`         | No                     | Retrieving Users whose Ids you know, for example from a webhook or from another data store. |
| `queryString` | Yes                    | Matching strings in one field or across all fields. |
| `query`       | Yes                    | Full Elasticsearch queries across fields, including nested values, ranges, and compound clauses. |
| `nextResults` | Yes                    | Paging past the first 10,000 results of a `queryString` or `query` search. Available in FusionAuth `1.48.0` and later. |

You can send any search as a `GET` or a `POST` request. Both methods return the same results. A `POST` request can hold a larger query, so the examples on this page use `POST`.

### Ids Searches

An `ids` search retrieves Users from the database by Id. An `ids` search never queries the search engine, so an `ids` search works even when the search engine is down.

### QueryString Searches

A `queryString` search matches without regard to case. URL-encode whitespace in a `GET` request, for example as `%20`. You can use Elasticsearch wildcards, such as `*` for a prefix or suffix match. To search one field, prefix the value with the field name, such as `email:`.

FusionAuth changes the `queryString` before sending the query to the search engine:

* When the value contains a `:`, FusionAuth sends the value as is.
* When the value contains an `@` and no spaces, FusionAuth treats the value as an email address and adds the `email:` prefix.
* When the value contains no spaces, FusionAuth adds a `*` wildcard to the start and the end.

<SearchPreprocessingWarning/>

The Admin UI changes the search value further, so a search in the Admin UI can return different results than the same value sent to the API.

Use `AND` and `OR` to combine clauses.

### Query Searches

The `query` parameter takes an Elasticsearch query as an escaped JSON string. FusionAuth passes the query to the search engine, so you can use the full Elasticsearch query language.

### Next Results Searches

<AvailableSince since="1.48.0"/>

Every `queryString` and `query` search returns a **`nextResults`** token. Send the token in the next request to get the page that follows the previous results. For an example, see [Extended Pagination](#extended-pagination).

### Field Mappings

`queryString` and `query` searches can match specific fields. For the fields you can search, see [Indexed User Fields](/docs/users/search/user-fields).

The search engine indexes the following relationships of each User as nested fields. To search nested fields, use a `query` search with the [nested query type](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/query-dsl-nested-query.html):

* `memberships`, the User's Group memberships
* `registrations`, the User's Application registrations

## Search With `query`

The `query` parameter takes an escaped Elasticsearch query, which FusionAuth passes to the search engine. A `query` search can use every feature of the Elasticsearch query language.

### Search One Field

First, build the Elasticsearch query. The following query matches every User with a **`user.data.Company`** value of `PiedPiper`.

<Aside type="note">
The **`user.data`** field holds any JSON, such as custom profile fields. Many FusionAuth objects have a **`data`** field, but the search engine indexes only **`user.data`**, **`registration.data`**, and **`entity.data`**.
</Aside>

The key is case-sensitive, so a search on `user.data.company` returns no Users. The value is case-insensitive, so `PiedPiper`, `piedpiper`, and `PIEDPIPER` return the same Users.

Next, escape the query. The FusionAuth request body is JSON, and the query is JSON inside a string, so you must escape the quotes and other JSON characters in the query. A `queryString` search doesn't need this step.

```shell-session title="Escaping Elasticsearch Query String using jq"
cat queryfile | jq -R -s '.'
```

## Search in the Admin UI

The Admin UI can build `queryString` and `query` values for the [User Search API](/docs/apis/users/search) and the [Bulk Delete Users API](/docs/apis/users/bulk-delete). Navigate to <Breadcrumb>Users</Breadcrumb>, and click <Breadcrumb>Advanced</Breadcrumb> below the **Search** field. The <Breadcrumb>Advanced</Breadcrumb> link appears only with the Elasticsearch search engine.

Pick values for common fields, or type a query string or JSON query in the search field. Turn on **Show Elasticsearch query** to see the query string or JSON query that the Admin UI sends. Copy the value into the **`queryString`** or **`query`** parameter of an API request.

The following screenshot shows a query string for Users in the `Moderators` Group and in the `Default` Tenant:

![The Advanced search form in the Admin UI, with a query string for Users in the Moderators Group of the Default Tenant.](/img/docs/get-started/core-concepts/user-search-query-string.png)

A search on an Application, or on a field of an Application, needs a JSON query, because the index maps registrations as nested fields. The following screenshot shows a JSON query for Users registered to the `Pied Piper` Application with the `CEO` role and an email address that matches `*@fusionauth.io`:

![The Advanced search form in the Admin UI, with a JSON query for Users registered to the Pied Piper Application with the CEO role.](/img/docs/get-started/core-concepts/user-search-json-query.png)

When a search matches more than 10,000 Users, click <Breadcrumb>Last</Breadcrumb> to go to the page with the 10,000th result. Then click <Breadcrumb>Next</Breadcrumb> to page forward one page at a time until the last result. In FusionAuth versions before `1.48.0`, paging past 10,000 results returns an error.

## Pagination

<PaginatingSearchResults />

In FusionAuth versions before `1.48.0`, a search returns at most 10,000 results, however you paginate. For workarounds, see [Limitations](#limitations).

### Extended Pagination

<AvailableSince since="1.48.0"/>

Every `queryString` and `query` search returns a **`nextResults`** token. Send the token in the next request, and FusionAuth returns the page that follows the previous results, with a new token. Repeat until a request returns no Users. With the token, you can page past the 10,000 result limit of `startRow`.

FusionAuth builds the query from the token, so a request with **`nextResults`** accepts only **`numberOfResults`** as another parameter. Internally, FusionAuth turns the token into an Elasticsearch `search_after` query. For more information, see the [Elasticsearch pagination documentation](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/paginate-search-results.html).

The following search finds all Users. The **`accurateTotal`** parameter returns the true count of matching Users instead of a count capped at 10,000:

<JSON title="Search Query To Find All Users" src="users/search-queryString-all-users-elasticsearch-request.json" />

The response includes a **`nextResults`** token:
