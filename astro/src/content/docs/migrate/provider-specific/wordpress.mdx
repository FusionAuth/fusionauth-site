## Overview

This guide moves users and their password hashes from WordPress to FusionAuth. The guide covers exporting the WordPress user tables, installing a password hashing plugin, and importing the users with scripts. To plan a migration at a higher level, see the [FusionAuth migration guide](/docs/migrate).

## Prerequisites

To import passwords as well as profile data, you need a basic understanding of password hashes and salts. For an introduction, see [The Math of Password Hashing Algorithms and Entropy](/articles/security/math-of-password-hashing-algorithms-entropy).

You need the following:

* [Node.js](https://nodejs.org/en) and npm, to run the migration scripts.
* [Docker](https://docs.docker.com/get-docker/), to run WordPress and FusionAuth locally with the configuration that this guide provides.

When you create an object with the FusionAuth API, you can set the object's Id. The Id must be a [UUID](/docs/apis/data-types#uuids). WordPress user Ids are integers, so FusionAuth can't reuse them. The import script stores each WordPress Id in **user.data.WordPress_ID**.

## Export Users

In this section, you start a sample WordPress site in Docker, look at the tables that hold users, and export the users with a SQL script.

### Clone the Code

Clone the FusionAuth import scripts repository, and change into the `wordpress` directory:

```shell-session
git clone https://github.com/FusionAuth/fusionauth-import-scripts.git && cd fusionauth-import-scripts/wordpress
```

### Start WordPress and FusionAuth

Start FusionAuth, WordPress, and their databases:

```shell-session
cd docker && docker compose up
```

When the containers start, open a second terminal in the `fusionauth-import-scripts/wordpress/docker` directory. Configure WordPress with the WordPress CLI:

```shell-session
docker compose exec cli wp core install --url="http://localhost:3000" --title="WP" --admin_user="admin" --admin_password="password" --admin_email="admin@example.org" --skip-email
```

To confirm that WordPress works, open [http://localhost:3000/wp-login.php](http://localhost:3000/wp-login.php) and log in with the username `admin` and the password `password`.

### Add a New User

In the second terminal, create an example user to migrate:

```shell-session
docker compose exec cli wp user create richard richard@example.org --role=subscriber --user_pass=password
```

### Explore the Users in the Database

Connect to the WordPress database with any MySQL client, such as [DBeaver](https://dbeaver.io/download). Use the following connection details:

* Host: `localhost`
* Port: `3306`
* Database: `mysite`
* Username: `admin`
* Password: `password`

WordPress keeps users in the `wp_users` and `wp_usermeta` tables.

#### The `wp_users` Table

The `wp_users` table holds the identifiers and the password hash of each user. The table looks similar to the following:

```plaintext
ID |user_login |user_pass                                                       |user_nicename |user_email          |user_url              |user_registered     |user_activation_key |user_status |display_name |
---|-----------|----------------------------------------------------------------|--------------|--------------------|----------------------|--------------------|--------------------|------------|-------------
 1 |admin      |$wp$2y$10$/hohy2X3tj5VXTbGNsgL5.gqWXv9fzjHkTsmqV4vHI4QyK351HyHy |admin         |admin@example.org   |http://localhost:3000 |2026-10-16 12:08:24 |                    |0           |admin        |
 2 |richard    |$wp$2y$10$IwsQg/CVVCPO6vUlnr68U.HEEbfAVpzjlITYjjUh7CGI.OkGu/gui |richard       |richard@example.org |                      |2026-10-16 12:08:25 |                    |0           |richard      |
```

The [WordPress Codex](https://codex.wordpress.org/Database_Description) lists the columns but doesn't define every column. The following definitions come from how WordPress uses each column:

* **ID**: The primary key, an auto-incremented integer.
* **user_login**: The username for logging in to WordPress.
* **user_pass**: The password hash.
* **user_nicename**: A URL-friendly version of the username, used in author URLs.
* **user_email**: The email address. Each user has a unique email address.
* **user_url**: The URL of the user's website. The field is optional.
* **user_registered**: The registration date and time, in `YYYY-MM-DD HH:MM:SS` format.
* **user_activation_key**: A hash for account activation or password resets.
* **user_status**: A deprecated field. Core WordPress doesn't use the field and leaves the value at `0`.
* **display_name**: The name that WordPress shows on posts and comments.

#### The `wp_usermeta` Table

The `wp_usermeta` table holds every other user detail. WordPress plugins can add rows too. The table looks similar to the following:

```plaintext
umeta_id|user_id|meta_key             |meta_value
--------|-------|---------------------|-------------------------------
1       |1      |nickname             |admin
2       |1      |first_name           |
3       |1      |last_name            |
4       |1      |description          |
5       |1      |rich_editing         |true
6       |1      |syntax_highlighting  |true
7       |1      |comment_shortcuts    |false
8       |1      |admin_color          |modern
9       |1      |use_ssl              |0
10      |1      |show_admin_bar_front |true
11      |1      |locale               |
12      |1      |wp_capabilities      |a:1:{s:13:"administrator";b:1;}
13      |1      |wp_user_level        |10
14      |1      |dismissed_wp_pointers|
15      |1      |show_welcome_panel   |1
16      |2      |nickname             |richard
17      |2      |first_name           |
18      |2      |last_name            |
19      |2      |description          |
20      |2      |rich_editing         |true
21      |2      |syntax_highlighting  |true
22      |2      |comment_shortcuts    |false
23      |2      |admin_color          |modern
24      |2      |use_ssl              |0
25      |2      |show_admin_bar_front |true
26      |2      |locale               |
27      |2      |wp_capabilities      |a:1:{s:10:"subscriber";b:1;}
28      |2      |wp_user_level        |0
29      |2      |dismissed_wp_pointers|
```

The table has the following columns:

* **umeta_id**: The primary key, an auto-incremented integer.
* **user_id**: The Id of the user that owns the row. The value matches the `ID` column of `wp_users`.
* **meta_key**: The name of the field.
* **meta_value**: The value of the field. A value can be a string or a serialized PHP array.

The table uses an entity-attribute-value model. WordPress adds a field by adding a row with a new key, not a new column.

When you decide which fields to import, consider the following:

* Skip blank fields, such as `description`.
* Skip fields that only WordPress uses, such as `rich_editing`.
* Skip legacy fields, such as `wp_user_level`.
* Deserialize fields that hold serialized PHP, such as `wp_capabilities`. The value `a:1:{s:13:"administrator";b:1;}` is an array of one element, with the 13-character string key `administrator` and the boolean value true.

You might find the following keys:

* **wp_capabilities**: The roles of the user, as a serialized array. The roles decide what the user can do in WordPress.
* **wp_user_level**: A legacy numeric user level, kept for backward compatibility.
* **rich_editing**: Whether the user writes with the visual editor, `true` or `false`.
* **syntax_highlighting**: Whether the code editor highlights syntax, `true` or `false`.
* **comment_shortcuts**: Whether the user moderates comments with keyboard shortcuts, `true` or `false`.
* **admin_color**: The color scheme of the WordPress dashboard.
* **use_ssl**: Whether WordPress forces SSL for the user's admin pages, `1` or `0`.
* **show_admin_bar_front**: Whether WordPress shows the admin bar when the user views the site, `true` or `false`.
* **locale**: The language of the WordPress dashboard.
* **wp_dashboard_quick_press_last_post_id**: The Id of the last post that the user created with the Quick Draft widget.
* **dismissed_wp_pointers**: The admin pointers that the user dismissed.
* **session_tokens**: The user's login sessions across devices.
* **wp_user-settings** and **wp_user-settings-time**: The user's admin area settings, and the time of the last change to the settings.

### Export the Users With SQL

FusionAuth provides the export and import scripts under a permissive open source license. The `wordpress/src` directory holds the scripts, and `wordpress/exampleData` holds sample output of each script.

In the second terminal, install the npm dependencies:

```shell-session
cd ../src && npm install
```

Run the remaining script commands in this `src` directory.

Run `1_exportWordpressUsers.sql` against the WordPress database. The script exports each row of `wp_users` as JSON, with the user's `wp_usermeta` fields in an array called `meta`. In DBeaver, view the output as text, and save the `json_result` column to a file called `users.txt` in the `src` directory.

<Aside type="note">
  When you have the `mysql` CLI installed, export the users from the command line instead:

  ```shell-session
  mysql -h 127.0.0.1 -P 3306 -u admin -ppassword mysite --raw < 1_exportWordpressUsers.sql > users.txt
  ```

  Then delete the `json_result` column name from the first line of `users.txt`.
</Aside>

Compare your `users.txt` file with `exampleData/1_wordpressExport/users.txt`. Each line of the file is a JSON object, but the file as a whole isn't valid JSON. Convert the file to a JSON array:

```shell-session
node 2_convertTextToJson.mjs
```

The script writes `users.json`. Compare the output with `exampleData/1_wordpressExport/users.json`.

## Import Users

To import the users, install a password hashing plugin that checks WordPress hashes, map the WordPress fields to FusionAuth fields, and run the import script.

### Use a WordPress Password Hash Plugin for FusionAuth

WordPress `6.8` and later hash passwords with [[bcrypt]], after an HMAC-SHA384 prehash of the password. FusionAuth supports plain bcrypt but not the prehashed WordPress format. Earlier WordPress versions hash passwords with phpass. FusionAuth supports phpass hashes natively with the `phpass-md5` scheme, but this guide's import script doesn't use the native scheme. For the schemes FusionAuth supports, see [Password-Hashing Algorithms](/docs/migrate/password-hashes/algorithms).

The [contributed password hashing plugins](https://github.com/FusionAuth/fusionauth-contrib/tree/main/Password%20Hashing%20Plugins) include a WordPress plugin that checks both formats. With the plugin, users from every WordPress version import with one scheme. For more information about plugins, see [Custom Password Hashing](/docs/migrate/password-hashes/custom-password-hashing).

<Aside type="note">
The plugin repository holds several projects. Build and install only the `Password Hashing Plugins` project.
</Aside>

Clone the plugin repository:

```shell-session
git clone https://github.com/fusionauth/fusionauth-contrib.git
```

The plugin code lives in `fusionauth-contrib/Password Hashing Plugins/src/main/java/com/mycompany/fusionauth/plugins/ExampleWordPressPhpassPasswordEncryptor.java`:

<ExtractedCode lang="java" src="configuration-snippets/contrib/password-hashing-plugins/ExampleWordPressPhpassPasswordEncryptor.java" />

Most hashing plugins take a plaintext password and a Base64 salt, and return a Base64 hash. A WordPress hash contains the salt and the cost, so the WordPress plugin works differently. The import script saves the full WordPress hash in the salt field. The `encrypt` function checks the password against that hash:

* When the password matches, `encrypt` returns the existing hash, so the hashes compare as equal.
* When the password doesn't match, `encrypt` returns a random number, so the hashes never compare as equal.
* When no existing hash exists, such as for a new password, `encrypt` returns a new phpass hash.

For a hash that starts with `$wp`, the plugin computes the same HMAC-SHA384 prehash as WordPress, and checks the prehash against the stored bcrypt hash.

The import script sets the factor to `8`. The plugin uses the factor only for new phpass hashes, because imported hashes contain their own cost.

The plugin has the following related files, which you shouldn't need to change:

* `fusionauth-contrib/Password Hashing Plugins/src/test/java/com/mycompany/fusionauth/plugins/ExampleWordPressPhpassPasswordEncryptorTest.java` holds the unit tests.
* `fusionauth-contrib/Password Hashing Plugins/src/main/java/com/mycompany/fusionauth/plugins/guice/MyExampleFusionAuthPluginModule.java` registers the plugin with FusionAuth.

A WordPress site can replace the default hashing algorithm, for example through a plugin. In that case, write your own Password Encryptor, add a test, and register the class in the Guice module.

WordPress hashes start with a prefix that names the algorithm:

* `$wp$2y$10$`: WordPress `6.8` and later. The hash is bcrypt, and the input is the Base64-encoded HMAC-SHA384 prehash of the password, with the key `wp-sha384`. `$2y$` marks bcrypt, and the number that follows is the cost.
* `$P$` followed by a cost character, such as `$P$B`: phpass, which iterates MD5. WordPress versions earlier than `6.8` use phpass.
* No prefix, 32 hexadecimal characters: plain MD5, from very old WordPress installations.
* `$1$`: MD5 crypt.
* `$2a$`, `$2x$`, or `$2y$`: bcrypt.
* `$5$` or `$6$`: SHA-256 crypt or SHA-512 crypt.
* `$argon2i$` or `$argon2id$`: Argon2.

The import script and the plugin handle only `$wp$` and `$P$` hashes. The import script stops with an error on any other format.

Build the plugin:

<Steps>

1. Open a terminal in the `fusionauth-contrib` directory. Build a Docker image for Java, and start a container with the repository mounted as a volume:

   ```shell-session
   cd .devcontainer && \
   docker build -t javaimage . && \
   cd .. && \
   docker run -it --name javabox -v .:/workspace javaimage
   ```

1. In the container, build the plugin and exit:

   ```shell-session
   cd "/workspace/Password Hashing Plugins" && \
   mvn clean install && \
   exit
   ```

</Steps>

When you have Java and Maven installed locally, run the `mvn clean install` command without Docker.

All tests pass, and Maven writes the plugin to `Password Hashing Plugins/target/fusionauth-example-password-encryptor-0.1.0.jar`.

### Set Up FusionAuth and Deploy the Plugin

FusionAuth already runs in the `fa` container from the earlier Docker Compose command. FusionAuth listens on `http://localhost:9011`. Log in to the [Admin UI](http://localhost:9011/admin) with `admin@example.com` and `password`.

Deploy the plugin:

<Steps>

1. In the `fusionauth-contrib` terminal, copy the jar file into the `plugins` directory of the FusionAuth container:

   ```shell-session
   docker exec fa mkdir /usr/local/fusionauth/plugins && \
   docker cp "Password Hashing Plugins/target/fusionauth-example-password-encryptor-0.1.0.jar" fa:/usr/local/fusionauth/plugins/fusionauth-example-password-encryptor-0.1.0.jar
   ```

1. Restart FusionAuth so FusionAuth loads the plugin. In the terminal that runs Docker Compose, press Ctrl+C, wait for the containers to stop, and run `docker compose up` again.

</Steps>

### Create Roles for Your Users

The `wp_capabilities` field gives the exported users the Administrator and Subscriber roles. In a terminal in the `fusionauth-import-scripts/wordpress/src` directory, create the roles in FusionAuth:

```shell-session

```

To see the roles, navigate to <Breadcrumb>Applications</Breadcrumb> in the Admin UI, and click <Breadcrumb>Select -> Manage Roles</Breadcrumb> in the row of `Example app`. ### Prepare Users for Import to FusionAuth

The `4_convertWpUserToFaUser.mjs` script maps the fields of `users.json` to FusionAuth fields. Change the script to skip fields or to map fields differently.

The script reads `users.json` with the [stream-json](https://github.com/uhop/stream-json) library, which reads large files incrementally. The `processUsers()` function calls `getFaUserFromUser()` for each user, and writes the results to `faUsers.json`.

The `getFaUserFromUser()` function does the following:

* Maps every WordPress field that has a matching FusionAuth field.
* Stores the other WordPress fields in the **data** field. To skip a field, add the field to the `dataToIgnore` list at the top of the file.
* Skips empty fields and arrays.
* Sets **encryptionScheme** to `example-wordpress-phpass`, the name that the Guice module gives the plugin.
* Adds a Registration for the Application, with the user's roles. Change the Application Id to match your Application in a real migration.

Helper functions at the bottom of the file read keys and values from the `meta` array and deserialize PHP values, such as `wp_capabilities`.

Read the function, and confirm that the script imports the user data that you need. Comment out the lines for data that you don't need. For more information about each user field, see the [Users API](/docs/apis/users).

Convert the users:

```shell-session
node 4_convertWpUserToFaUser.mjs
```

### Use the Script

With `faUsers.json` created and the plugin installed, import the users. In a terminal in the `fusionauth-import-scripts/wordpress/src` directory, run the import script:

```shell-session
node 5_import.mjs
```

The script calls `importUsers()` from the FusionAuth Node.js client library, `@fusionauth/typescript-client`. For more information, see the [TypeScript client library](/docs/sdks/typescript).

The script imports one user per request. When the import runs too slowly for a production migration, send users in batches of 1000.

## What To Do Next

phpass is a weak algorithm. When you import phpass hashes from WordPress versions earlier than `6.8`, rehash the passwords with a stronger scheme at each user's next login. For more information, see [Rehashing User Passwords](/docs/migrate/password-hashes/custom-password-hashing#rehashing-user-passwords).
