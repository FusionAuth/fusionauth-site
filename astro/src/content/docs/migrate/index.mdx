FusionAuth can import user data from a homegrown system or from another identity provider. An import can carry profile data, roles, groups, registrations, refresh tokens, and password hashes. FusionAuth stores fields without a FusionAuth equivalent in **`user.data`**.

## Import Users

FusionAuth offers the following ways to bring users in:

* The [Import Users API](/docs/apis/users/import) loads users in batches, with their existing password hashes. Use the Import Users API for a bulk migration.
* The [Create a User API](/docs/apis/users/create) creates one user at a time. The Create a User API takes a plaintext password or no password, not a hash. Use the Create a User API for a few users, for users without passwords, or for an instance that already has users.
* [Connectors](/docs/users/provision/connectors) move each user at the user's first login. Use Connectors for a slow migration when you can't export password hashes. Connectors require the Starter plan or higher.
* [[SCIM]] provisions users from a SCIM client, such as Azure AD or Okta, and keeps the accounts in sync. SCIM requires the Enterprise plan. For more information, see [SCIM](/docs/users/provision/scim).

To choose an approach, see [Migration Types](/docs/migrate/migration-types). To work through a migration from start to finish, follow these pages in order:

1. [Plan a Migration](/docs/migrate/plan-a-migration) maps your data to FusionAuth and sets up FusionAuth.
1. [Bulk Migration](/docs/migrate/bulk-migration) or [Slow Migration](/docs/migrate/slow-migration) moves the users.
1. [Special Considerations](/docs/migrate/special-considerations) covers refresh tokens, SAML configuration, very large user counts, and applications that depend on the old system's tokens.

For a worked example with one user table, see the [Generic Migration Tutorial](/docs/migrate/genericmigration).

## Use FusionAuth Without Importing Users

FusionAuth can authenticate users against an existing user store without storing the users:

* When the user store supports SAML or OIDC, configure the store as an [Identity Provider](/docs/concepts/identity-providers). Customize the theme, and consider a login hint to send users straight to the store.
* When the user store supports [[LDAP]] or a JSON API, configure a [Connector](/docs/users/provision/connectors) without migration.

In both cases, FusionAuth talks to the user store through an interface, never through the store's database. FusionAuth doesn't support direct database access.
