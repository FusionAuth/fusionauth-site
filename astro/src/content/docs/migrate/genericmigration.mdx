This tutorial migrates the users of a small Express app with custom authentication to FusionAuth. The tutorial covers exporting password hashes, mapping users to FusionAuth fields, importing users with the API, and switching the app to log in through FusionAuth. To plan a migration at a higher level, see the [FusionAuth migration guide](/docs/migrate).

## Prerequisites

To import passwords along with personal details, you need a basic understanding of password hashes and salts. For an introduction, see [The Math of Password Hashing Algorithms And Entropy](/articles/security/math-of-password-hashing-algorithms-entropy).

The example app, the migration scripts, and FusionAuth run in [Docker](https://docs.docker.com/get-docker/).

<Aside>
  When your hosts file has no entry for `host.docker.internal`, add one. On macOS and Linux, run the following command:

  ```shell
  echo "127.0.0.1 host.docker.internal" | sudo tee -a /etc/hosts
  ```
</Aside>

To run the scripts on your machine instead of in Docker, install Node.js. Then replace `db` and `host.docker.internal` with `localhost` in every script.

* When your application uses roles, FusionAuth configures [roles](/docs/concepts/types/roles) per application. FusionAuth adds a user's roles to the token after a successful login.
* To manage separate sets of users, use [Tenants](/docs/concepts/types/tenants).
* When your application sends emails, such as forgot password notifications, FusionAuth sends the same emails with customizable templates. For more information, see [Email Templates](/docs/email/email-templates).
* FusionAuth stores custom user attributes in the **`user.data`** field. The field accepts any valid JSON value, has no size limit, and is searchable.
* When your application uses multi-factor authentication (MFA), turn on MFA in FusionAuth. For more information, see [Multi-Factor Authentication](/docs/authentication/multi-factor-authentication).

#### Identifiers

When you create an object with the FusionAuth API, you can set the object's Id. The Id must be a [UUID](/docs/apis/data-types#uuids). Users, Applications, Tenants, and most other objects accept an Id.

## Exporting Users

The example app has a sign-in page, a restricted account page, and a PostgreSQL database with one table of users and password hashes.

### Start the Example App

Clone the import scripts repository:

```shell-session
git clone https://github.com/FusionAuth/fusionauth-import-scripts
```

The `generic` directory holds the code for this tutorial. The `generic/exampleData` directory holds sample output from the scripts.

Start the app and the app's database in Docker:

```shell-session
cd fusionauth-import-scripts/generic/src
docker compose --file 1_appDockerCompose.yaml up
```

### Create the User Table

Open a new terminal in the `fusionauth-import-scripts/generic/src` directory. Open a shell in the app container:

```shell-session
docker exec --interactive --tty app sh
```

Run every script in the rest of the tutorial in this container shell. Install the dependencies, and create the user table:

```shell-session
cd /workspace && \
npm install && \
node 2_createUser.mjs
```

The `2_createUser.mjs` script creates a `user` table with the text columns `email`, `hash`, and `salt`.

To browse the table, connect a PostgreSQL client such as [DBeaver](https://dbeaver.io/download) to `localhost` on port `7770`. Use the database `p`, the username `p`, and the password `p`.

### Run the Web App

In the container shell, start the Express app:

```shell-session
node 3_webApp.mjs
```

Browse to `http://localhost:7771/account`. The account page is restricted, so the app denies access.

Browse to `http://localhost:7771`, and sign in with the email `user@example.com` and the password `password`. The app creates the user in the database and redirects you to the account page. The app now stores your email address in the session, so the account page shows your details.

The app in `3_webApp.mjs` has GET routes for the home page and the account page. The POST route for the home page does the following:

* Rejects the request when the email or password is missing.
* Looks up the email in the database.
* When the email exists, hashes the entered password with the stored salt and compares the result with the stored hash.
* When the email doesn't exist, creates the user with a random UUID as the salt.

The `getHash` function at the end of the file hashes the password and salt with 20,000 rounds of SHA-256. FusionAuth supports this scheme natively as `salted-sha256`. For more information, see [Salted SHA-256](/docs/migrate/password-hashes/algorithms#salted-sha-256). When your app uses a scheme that FusionAuth doesn't support, see [Writing a Plugin](/docs/migrate/password-hashes/writing-a-plugin).

Press `Ctrl+C` in the container shell to stop the app.

### Create a Users File

In the container shell, export the users to `users.json`:

```shell-session
node 4_exportUsers.mjs
```

For a real app, write the export in any language. A SQL query against your database is the most common choice.

The `5_convertUserToFaUser.mjs` script maps the fields in `users.json` to FusionAuth User fields. The example app stores only an email and a password, so a real app needs a larger mapping. For the full list of User fields, see the [Users API](/docs/apis/users).

The script reads `users.json` with [`stream-json`](https://github.com/uhop/stream-json), which reads a file incrementally and handles files with millions of users. The `processUsers()` function passes each user to `getFaUserFromUser()` and writes the result to `faUsers.json`.

The `getFaUserFromUser()` function does the following:

* Copies the fields that match FusionAuth fields.
* Sets **`encryptionScheme`** to `salted-sha256` and **`factor`** to `20000`.
* Converts the salt to Base64, the format that FusionAuth expects.
* Adds a registration for the Test application. Change the Application Id to your own for a real migration.
* Sets **`data.ImportedFromExpressJs`** to `true`. Store any field without a FusionAuth equivalent in **`data`**.

Run the script in the container shell:

```shell-session
node 5_convertUserToFaUser.mjs
```

The output is a JSON array like the one in `fusionauth-import-scripts/generic/exampleData/faUsers.json`.

## Importing Users

To start a FusionAuth instance for testing, open a new terminal in the `fusionauth-import-scripts` directory and run the following commands:

```shell-session
cd generic/fusionAuthDockerFiles && \
docker compose up
```

FusionAuth runs at `http://localhost:9011` in a container named `fa`. Log in to the [Admin UI](http://localhost:9011/admin) with the email `admin@example.com` and the password `password`.

The instance configures itself with [[Kickstart]] from `generic/fusionAuthDockerFiles/kickstart/kickstart.json`. The Kickstart file creates an API key, an admin user, a theme, and the Test application. For more information, see [Kickstart](/docs/get-started/develop/kickstart).

In the container shell, import the users from `faUsers.json`:

```shell-session
node 6_importUsers.mjs
```

The script calls `importUsers()` from the [TypeScript client library](/docs/sdks/typescript) once for each user. For a large migration, send many users in each call. For batch sizes, see the [Import Users API](/docs/apis/users/import).

## Use FusionAuth as Your Authentication Provider

To switch the example app to log in through FusionAuth:

<Steps>

1. In the [Admin UI](http://localhost:9011/admin), navigate to <Breadcrumb>Applications</Breadcrumb>. Click <Breadcrumb>Select</Breadcrumb> for the Test application, and choose <Breadcrumb>Edit</Breadcrumb>.
1. On the <Breadcrumb>OAuth</Breadcrumb> tab, set **Authorized redirect URLs** to `http://localhost:7771/callback`, which is the app's [[callback URL]].

    <Screenshot id="migration-example-app-redirect" url="/admin/application/edit?applicationId=e9fdb985-9173-4e01-9d73-ac2d60d1dc8e&tenantId=30663132-6464-6665-3032-326466613934#oauth" showHash crop="[data-migration-window]" cropPadding={0} chrome={true} alt="The authorized redirect URL on the application OAuth tab.">
      <Highlight selector="[data-hl='migration-redirect']" />
    </Screenshot>

1. Click <Breadcrumb>Save</Breadcrumb>.
1. In the container shell, start the version of the app that uses FusionAuth:

    ```shell-session
    node 7_webAppWithFa.mjs
    ```

1. Browse to `http://localhost:7771`. FusionAuth shows the login page in place of the app's sign-in page.

</Steps>

The new app matches the original, except that OAuth calls to FusionAuth through [Passport](https://www.npmjs.com/package/passport) replace the login and hashing code. To style the login page, or for a full walkthrough of an Express integration, see the [Express QuickStart](/docs/quickstarts/web/express).

<Aside type="caution">
  The `authOptions` object at the end of `7_webAppWithFa.mjs` stores secrets in the code. In a real app, move the secrets to a `.env` file that stays out of source control. For URLs that the server calls, use `host.docker.internal` instead of `localhost`. Browser URLs keep `localhost`.
</Aside>

### Delete the Docker Containers

Press `Ctrl+C` in every terminal to stop the containers. When you finish testing, remove the containers and images from your machine:

```shell-session
docker rm app app_db fa fa_db && \
docker rmi postgres:16.2-alpine3.19 node:alpine3.19 fusionauth/fusionauth-app:latest postgres:16.0-bookworm
```

## What to Do Next

The example app hashes passwords with salted SHA-256, which is weaker than modern schemes. To rehash each password with a stronger scheme at the user's next login, turn on **Re-hash on login or change** in the Tenant. For more information, see [Rehashing User Passwords](/docs/migrate/password-hashes/custom-password-hashing#rehashing-user-passwords).
