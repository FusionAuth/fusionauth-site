## Field Lengths

FusionAuth stores most data in a database. The database schema for your database type sets the maximum length of each column. To look up the length of a column, [download the database schema for your version of FusionAuth](/direct-download).

Many `VARCHAR` columns have a length of 191 characters. The length comes from MySQL 5.7, where the InnoDB engine limited an index key to 767 bytes. The `utf8mb4` character set uses up to 4 bytes per character, and 767 / 4 rounds down to 191.

## Data Field Sizes

FusionAuth stores the **`data`** field of an object in a single database column. The column type sets the maximum size, and the maximum depends on your database:

| Object | MySQL | PostgreSQL |
|---|---|---|
| Users, Registrations, Groups, Group Members, Consents, Audit Logs | 16,777,215 bytes (16 MB) | About 1 GB |
| Applications, Tenants, Entities, Entity Types, Entity Type Permissions, Entity Grants, Forms, Form Fields, Webhooks, Connectors, Messengers, Message Templates, OAuth Scopes, CIMD Domains | 65,535 bytes (64 KB) | About 1 GB |
| Themes, System Configuration | About 4 GB | About 1 GB |

The column holds more than the **`data`** field. FusionAuth serializes the **`data`** field and the object fields that have no column of their own into the column as JSON:

* For Users, the column also holds **`preferredLanguages`** and **`twoFactor`**.
* For Registrations, the column also holds **`preferredLanguages`** and **`tokens`**.
* For Applications and Tenants, the column holds the entire configuration of the object. A new Application or Tenant uses about 2 KB to 4 KB of the column before you add custom data, so less than 64 KB remains for the **`data`** field on MySQL.

MySQL measures the limit in bytes, not characters. `utf8mb4` stores a character outside ASCII in 2 to 4 bytes, so fewer characters fit in the column.

FusionAuth also limits every API request, on any database. On PostgreSQL, the following request limits apply long before the column fills:

* A request body can hold up to 128 MB by default. FusionAuth rejects a larger request with a `413` status code and an empty response. To change the maximum, set `fusionauth-app.http.max-request-size`. For more information, see the [Configuration reference](/docs/deploy/production/configuration).
* A single JSON string value can hold up to 20,000,000 characters. FusionAuth rejects a longer string with a `400` status code and an `[invalidJSON]` field error. To store more data, split the data across several keys in the **`data`** field.

FusionAuth doesn't validate the size of a **`data`** field against the column size. On MySQL, when the serialized JSON exceeds the column size, MySQL rejects the write. The API then returns a `500` status code with the `[Exception]` general error code, and FusionAuth logs a `Data too long for column 'data'` error. FusionAuth saves nothing from the request, and the existing object stays unchanged.

Keep **`user.data`** and **`registration.data`** small, even when the database allows more. FusionAuth loads the User and the User's Registrations on every login, and the [Login API](/docs/apis/login) returns the full User in the response. A User with 16 MB of custom data produces a 16 MB login response. When you use the Elasticsearch search engine, FusionAuth also indexes **`user.data`**, **`registration.data`**, and **`entity.data`**, so large values increase the size of the search index. To keep large records, such as documents or files, store the records in another system and save an Id or URL in the **`data`** field.

## API Keys

FusionAuth is API first and everything can be managed by an API. You can create an API key in the following ways:

* Using the [API Key API](/docs/apis/api-keys), if you are using version 1.26 or greater.
* Use the Admin UI.
* [Kickstart](/docs/get-started/develop/kickstart) which only works on fresh installations.

## Minimum Key Lengths

You can use FusionAuth to manage your cryptographic keys. Due to security considerations, FusionAuth won't import keys below a certain length.

For RSA keys used to verify signatures, the minimum length is 1024. This key length is allowed as of FusionAuth 1.23.4 and supports external systems that rely upon this weak key length.

For RSA keys used for signing or any other purpose, the minimum length is 2048.

For ECC keys, the minimum length is 256.

See the [Keys API](/docs/apis/keys) for more, including supported algorithms and lengths.

## Generated Certificates

Certificates that Key Master generates for RSA and elliptic curve key pairs are self-signed X.509 version 2 certificates, with no X.509 v3 extensions. To use a v3 certificate, create the certificate and private key outside FusionAuth, and import both. For more information, see [Importing vs Generating](/docs/security/tokens-and-keys/key-master#importing-vs-generating).

## Identifiers

Identifiers (Ids) in FusionAuth are [UUIDs](/docs/apis/data-types#uuids).

If you are creating an object, such as an Application, with the FusionAuth API, you can specify this Id, as long as it is a valid UUID. The ability to choose specific Ids exists for Users, Applications, and Tenants, among others, and allows you to avoid breaking external systems dependent on existing identifiers.

Ids cannot be modified after the object is created. If you need to change an identifier, delete the object and recreate it with the correct Id.

### User Identifiers

Each account must have an identifier, either an email address or a username. Users may not have multiple email addresses. See [this issue for more information](https://github.com/fusionauth/fusionauth-issues/issues/1).

An account may have both a username and an email address.

### Client Ids

OAuth has the concept of a `client_id`. In FusionAuth, `client_id`s cannot be modified after creation. During creation, an Id can be set to any valid UUID value. The Id must be unique across all Tenants.

The `client_id` is always the same as either the Application Id or Entity Id, depending on the grant you are using.

## What's Not Limited

All other objects and configuration, including but not limited to the following, are limited only by the resources of your system:

* Users
* Applications
* Tenants
* Roles
* Groups
* Identity Providers such as SAML or OIDC connections
* API keys to allow for programmatic configuration of and interaction with FusionAuth
* The number of email templates
* Supported languages/locales
* Signing and verifying keys
* MFA methods per user
