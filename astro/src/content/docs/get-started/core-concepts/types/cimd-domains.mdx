Client ID Metadata Documents (CIMD) is an OAuth extension, described by [draft-ietf-oauth-client-id-metadata-document](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/), in which the `client_id` is itself an HTTPS URL. That URL hosts a JSON document describing the client: its name, its redirect URIs, and the rest of its metadata.

When a client presents such a `client_id`, FusionAuth fetches the document, validates it, caches it, and registers the client just-in-time. Once you've configured a CIMD domain for that origin, neither you nor the client's developer has to register each individual client ahead of time.

CIMD addresses a trust issue with [Model Context Protocol (MCP)](https://modelcontextprotocol.io/seps/991-enable-url-based-client-registration-using-oauth-c) clients: clients (e.g. `claude.ai`) cannot preregister with every MCP server. CIMD provides a way to dynamically register MCP clients with your MCP server. [Dynamic Client Registration (DCR)](/blog/cimd-vs-dcr) previously solved the same problem, but CIMD involves less state and complexity.


## CIMD Domains

CIMD configuration starts with a **CIMD domain**, which names one origin that clients may register from (e.g. `https://claude.ai`). You configure CIMD domains at the [Tenant](/docs/get-started/core-concepts/types/tenants) level.

CIMD domains do not support:

* paths, query strings, or fragments
* wildcards (e.g. `https://*.example.com`)
* bare IP addresses
* `localhost`
* loopback addresses.

To register a client from any origin, specify a CIMD domain with the wildcard `*`. Since the wildcard matches any domain, you cannot specify specific domains in addition to the wildcard. However, you can use a [registration Lambda](/docs/extend/code/lambdas) to filter clients even when you allow any domain with the wildcard.

FusionAuth also validates the Client Ids provided in client metadata. Client Ids must:

* use HTTPS
* include a path
* contain no fragment and no userinfo component
* be no longer than 2048 characters
* match one of the tenant's CIMD domains (or the wildcard)

### Fixed OAuth Behavior

The CIMD standard requires the following security measures:

* Clients must implement [PKCE](/articles/oauth/modern-guide-to-oauth#authorization-code-grant).
* Clients can only use the `authorization_code` and `refresh_token` grants.
* Redirect URLs must exactly match the redirect URIs specified in the client's metadata document. The only exception is the port of an `http` loopback redirect URI, which can differ, as described in [RFC 8252](https://datatracker.ietf.org/doc/html/rfc8252#section-7.3).
* Clients can only request scopes enabled on the domain, or the OAuth request will fail. Optional scopes the user declines on the consent screen are left out of the grant.
* Clients must send exactly one `resource` parameter, and it must be one of the domain's **Authorized resource URIs**.
* CIMD clients cannot use roles, SAML, WebAuthn, and self-service registration.
* A client's MFA trust only comes from logins through the same CIMD domain.
* Many CIMD clients are public, so client authentication is not required.
* The CIMD domain's Id isn't a valid `client_id`. FusionAuth rejects it with an `invalid_client` error. An Application can't use the same Id as a CIMD domain.

### Identity Providers

Users can log in to CIMD clients with an [identity provider](/docs/lifecycle/authenticate-users/identity-providers/), such as Google or a SAML v2 provider. Each CIMD domain appears in the identity provider's application list as `CIMD: <domain>`, such as `CIMD: https://claude.ai`. Enable the identity provider for that entry to offer it to the domain's clients. When using the API, use the CIMD domain's Id as the application Id in the identity provider's **applicationConfiguration**.

The following restrictions apply:

* An identity provider can't create user registrations for a CIMD domain. FusionAuth ignores **createRegistration** for a CIMD domain, and the admin UI disables it.
* A SAML v2 identity provider with IdP-initiated login enabled can't be enabled for a CIMD domain. FusionAuth rejects the configuration with a validation error. The [SAML v2 IdP Initiated](/docs/lifecycle/authenticate-users/identity-providers/enterprise/samlv2-idp-initiated) identity provider doesn't list CIMD domains.

### Hosted Login Pages

<AvailableSince since="1.70.0" />

CIMD clients log in through the FusionAuth [hosted login pages](/docs/get-started/core-concepts/hosted-login-vs-api-login#hosted-login-pages), with these differences:

* Users are not registered for CIMD clients. The `userState` returned to the client is always `AuthenticatedNotRegistered`.
* Every OAuth request must include the Tenant Id, because the `client_id` URL does not identify a Tenant. Use the Tenant's endpoints, such as `/oauth2/authorize/{tenantId}`.
* Users cannot log in with a [magic link](/docs/lifecycle/authenticate-users/one-time-passwords) or a [passkey](/docs/lifecycle/authenticate-users/passkeys). The login page does not show these options.
* FusionAuth prompts for consent even when the client requests no scopes. The prompt shows the client's name and where its metadata document is hosted. See [Consent Prompt](/docs/lifecycle/authenticate-users/oauth/scopes#cimd-clients).
* You can enable [identity providers](/docs/lifecycle/authenticate-users/identity-providers/#cimd-clients) for the CIMD clients of a domain, except for IdP-initiated SAML.

## Managing CIMD Domains

Click <Breadcrumb>CIMD Domains</Breadcrumb> in the left navigation to see every CIMD domain in the tenants you can administer.

<Screenshot id="cimd-domain-list" url="/admin/cimd-domain/" alt="The CIMD Domains list page." />

From here you can see each domain's name, origin, and consent mode, search by name or Id, and filter by Tenant. When you have more than one Tenant, the list also shows each domain's Tenant. You can also:

- **Create** a new CIMD domain.
- **Edit** a previously created CIMD domain.
- **Manage scopes** for a previously created CIMD domain.
- **View** a previously created CIMD domain.
- **Delete** a previously created CIMD domain.

Managing CIMD domains requires the `admin` or `cimd_domain_manager` role. Deleting a CIMD domain requires the `admin` or `cimd_domain_deleter` role. To manage CIMD domains via the API, an API key needs permission for the relevant [CIMD Domain APIs](/docs/apis/cimd-domains) endpoints.

#### Form Fields

<APIBlock>
  <APIField name="ID" optional>
    An optional UUID. When this value is omitted a unique Id will be generated automatically. This value cannot be changed after creation. CIMD domain Ids are unique across all tenants.
  </APIField>
  <APIField name="Name" optional>
    A name used to identify the CIMD domain in the admin UI. Leave it blank to use the **Domain** value as the name.
  </APIField>
  <APIField name="Tenant" required>
    The Tenant this CIMD domain belongs to. This value cannot be changed after creation.
  </APIField>
</APIBlock>

#### General Tab

<APIBlock>
  <APIField name="Domain" required>
    The origin CIMD clients register from, including the scheme, hostname, and optional port of the URL where FusionAuth expects to find the CIMD document. FusionAuth uses this to validate each client's `client_id` URL. Use `*` to allow CIMD registrations from any domain. This value cannot be changed after creation.
  </APIField>
  <APIField name="Authorized resource URIs" optional>
    The resource URIs that clients on this domain may request using the [RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707) `resource` parameter. Every CIMD client must send exactly one `resource`, and FusionAuth rejects the request with `invalid_target` unless it appears in this list. Clients on a domain with no authorized resource URIs cannot log in.
  </APIField>
  <APIField name="Allow localhost redirect URIs" optional defaults="false">
    When enabled, CIMD clients on this domain may use a `localhost` redirect URI that appears in their metadata document. Loopback IP addresses such as `127.0.0.1` are always allowed. [RFC 8252](https://datatracker.ietf.org/doc/html/rfc8252#section-7.3) recommends loopback IP addresses over `localhost`, so enable this only for CIMD clients that require it.
  </APIField>
  <APIField name="Enable debug logging" optional defaults="false">
    When enabled, FusionAuth writes the standard OAuth debug Event Log entries, such as the authorization code exchange, for this domain's clients. View them under <Breadcrumb>System -> Event Log</Breadcrumb>. The authorization code exchange entry lists the requested resources. FusionAuth also writes a Debug entry when it creates a client registration, refreshes one after its cache expires, or adds a new resource to an existing one. FusionAuth always writes an Error entry for a failed client registration, whether or not this is enabled. It always writes an Information entry when it rate limits a registration.
  </APIField>
  <APIField name="Minimum cache duration" readonly defaults="900">
    The shortest time, in seconds, that a client's CIMD document is cached. This value is always 15 minutes and can't be changed.
  </APIField>
  <APIField name="Maximum cache duration" required defaults="86400">
    The longest time, in seconds, that a client's CIMD document is cached. When the document's response includes a smaller `Cache-Control: max-age` value, the smaller value is used. When the response has no `max-age`, the document is cached for 15 minutes. This value must be at least `900`. See [CIMD Registration Caching And Lifecycle](/docs/lifecycle/authenticate-users/oauth/cimd-registration-lifecycle#how-long-fusionauth-caches-a-document).
  </APIField>
  <APIField name="Grace period" required defaults="0">
    How long, in seconds, to honor an expired CIMD document when re-fetching it fails. See [CIMD Registration Caching And Lifecycle](/docs/lifecycle/authenticate-users/oauth/cimd-registration-lifecycle#the-grace-period).
  </APIField>
</APIBlock>

#### Scopes Tab

<APIBlock>
  <APIField name="Consent mode" required defaults="Always prompt">
    Whether users must grant consent each time scopes are requested, or whether FusionAuth remembers their decision. The available values are `Always prompt` and `Remember decision`. A CIMD domain cannot skip the consent prompt entirely. FusionAuth remembers a decision separately for each client and `resource`. Changing this to `Always prompt` deletes every remembered decision for the domain's clients.
  </APIField>
  <APIField name="Provided scopes" optional>
    Controls how FusionAuth handles the standard OpenID Connect scopes (`address`, `email`, `phone`, and `profile`) for clients on this domain. Marking a scope **Enabled** allows clients to request it; a disabled scope is treated as unknown and will fail the request. Marking a scope **Required** means users must consent to it before they can complete authorization. Each scope is enabled and not required by default.

    The `offline_access` scope is always enabled and cannot be turned off. When a client requests it, a refresh token is issued alongside the access and Id tokens, governed by the Tenant's refresh token settings. It is not shown on the consent screen.
  </APIField>
</APIBlock>

Custom scopes beyond the standard ones are managed separately, through the **Manage scopes** action on a saved domain, or through the [CIMD Domain OAuth Scopes API](/docs/apis/cimd-domain-scopes). They are available to every client that registers through the domain.

#### Lambdas Tab

<APIBlock>
  <APIField name="Registration lambda" optional>
    A [CIMD client registration lambda](/docs/extend/code/lambdas/cimd-client-registration) that can override registration decisions and scopes for this domain's clients. This is the only way to filter which clients may register when the **Domain** is `*`. No lambda is selected by default.
  </APIField>
  <APIField name="JWT populate lambda" optional>
    A [JWT populate lambda](/docs/extend/code/lambdas/jwt-populate) that adds or modifies claims in the tokens issued to this domain's clients. The selected lambda populates both the access token and the Id token. No lambda is selected by default.
  </APIField>
</APIBlock>

### Remove a CIMD Domain

When a CIMD domain is no longer needed, it can be removed by clicking the <Icon name="trash"/> action:

<Screenshot id="cimd-domain-delete" url="/admin/cimd-domain/delete/7d3c9a2e-41f6-4b8e-9c05-2e6f1a8b3d47" alt="The Remove CIMD domain confirmation." />

<Aside type="caution">
Deleting a CIMD domain is permanent and cannot be reversed. It removes every client registered through the domain and revokes those clients' refresh tokens. Clients from the domain can no longer register or authenticate.
</Aside>

When you add, update, or delete a CIMD domain in the admin UI, FusionAuth records the change in the [Audit Log](/docs/apis/audit-logs). It does the same when you add, update, or delete one of the domain's custom scopes.

### Manage CIMD Domain Scopes

Click the <Icon name="code"/> action on a CIMD domain to add and manage its custom OAuth scopes. These scopes are available to every client that registers through the domain, in addition to the standard OpenID Connect scopes enabled on the <Breadcrumb>Scopes</Breadcrumb> tab.

<Screenshot id="cimd-domain-scope-list" url="/admin/cimd-domain/manage-scopes?domainId=7d3c9a2e-41f6-4b8e-9c05-2e6f1a8b3d47" alt="The Manage Scopes page for a CIMD domain." />

Click the **Add** button to create a new custom scope:

<Screenshot id="cimd-domain-scope-add" url="/admin/cimd-domain/manage-scopes?domainId=7d3c9a2e-41f6-4b8e-9c05-2e6f1a8b3d47" alt="The Add scope form." />

Editing a saved scope presents a similar form that also shows the scope's **Id**. The **Id** and **Name** values are read-only:

<Screenshot id="cimd-domain-scope-edit" url="/admin/cimd-domain/manage-scopes?domainId=7d3c9a2e-41f6-4b8e-9c05-2e6f1a8b3d47" alt="The Edit scope form." />

A custom scope can also be removed from the same row's action menu. This cannot be reversed. A client that registers after the removal fails if it requests the removed scope, because a CIMD domain always rejects unknown scopes.

FusionAuth saves a copy of the domain's scope settings in each client's registration, so changes to scopes, provided scopes, or authorized resource URIs don't apply to an already-registered client until FusionAuth fetches its document again. See [CIMD Registration Caching And Lifecycle](/docs/lifecycle/authenticate-users/oauth/cimd-registration-lifecycle) for when that happens.

#### Form Fields

<APIBlock>
  <APIField name="Id" readonly>
    The Id of the OAuth scope, generated automatically when the scope is created. This field only appears when editing a scope. To choose your own Id, create the scope with the [CIMD Domain OAuth Scopes API](/docs/apis/cimd-domain-scopes).
  </APIField>
  <APIField name="Name" required>
    The name of the OAuth scope. This is the value that will be used to request the scope. This value cannot be changed after creation.
  </APIField>
  <APIField name="Description" optional>
    A description of the OAuth scope for internal use.
  </APIField>
  <APIField name="Consent message" optional>
    The default message to display on the OAuth consent screen if one cannot be found in the theme.
    [Learn more about setting this value using themes.](/docs/theme/localization#oauth-scope-consent-prompt)
  </APIField>
  <APIField name="Consent details" optional>
    The default detail to display on the OAuth consent screen if one cannot be found in the theme.
    [Learn more about setting this value using themes.](/docs/theme/localization#oauth-scope-consent-prompt)
  </APIField>
  <APIField name="Required" optional>
    Determines if the OAuth scope is required when requested by a client.
  </APIField>
</APIBlock>

## Configure CIMD Domains With the API

Everything on this page can also be configured through the API:

* Use the [CIMD Domain API](/docs/apis/cimd-domains) to create, retrieve, update, search, and delete CIMD domains.
* Use the [CIMD Domain OAuth Scopes API](/docs/apis/cimd-domain-scopes) to manage a domain's custom OAuth scopes.
* Use the [CIMD Client Registration API](/docs/apis/cimd-client-registrations) to retrieve, search for, and delete the clients registered through a domain. The admin UI doesn't show these registrations.
