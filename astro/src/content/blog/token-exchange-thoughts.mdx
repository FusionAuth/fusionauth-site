Token exchange is what you reach for when a token you already have is the wrong shape for the place you need to use it.

{/* more */}

Say a user logs in and your frontend gets an access token for your main API. That API calls a billing service, which calls a reporting service, and each of those wants a token with its own audience and just the scopes it needs.

You could pass the original token all the way down. And plenty of people do, which is how you end up with one stolen token that works everywhere. Or you could have each service trade the token it received for a narrower one useful for the next service. The user’s identity travels with the request but the blast radius doesn't. This trade is not cost-free since it adds latency and a dependency on the component performing it, but it also increases security and lessens system cohesion.

That trade is what the token exchange is for. Token exchange is a [standard OAuth grant](/articles/oauth/complete-list-oauth-grants#oauth-20-token-exchange-grant) that lets you provide a token to an authorization server and have that authorization server issue a new token. The token exchange standardizes a set of parameters which define, among other things, the type of token presented, the desired resource or audience and the resulting token's claims. The latter includes standard claims such as the `client_id`, the identifier of the client making the exchange and `act`, a compound claim containing the party to which delegation has occurred.

Token exchange is a feature most teams don't require until they need it, and then they need it badly. If you have a monolith and a few APIs, ignore this grant; it's extra complexity. Once you have services calling services on behalf of users, you’re making a choice whether you realize it or not. Either you’re exchanging tokens deliberately, or you’re forwarding whatever you were handed and hoping nobody downstream is compromised or buggy. When your reporting service gets a request, do you actually know whether the token it receives was meant for it?

## Multiple use cases, one RFC

If you look at [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693), you'll see multiple use cases outlined. 

The first is impersonation. Impersonation is where you are acting as somebody else and the token you hold looks like that person's. The canonical use case is a customer service rep who says to the authorization server "I have permission to act as Dan Moore in this application, please give me a token that lets me do that." The identity system records the impersonation exchange, but the issued token is indistinguishable from one obtained by the original user. Making this request requires an elevated set of permissions.

The second use case in the RFC is delegation. In that case, there is a second entity explicitly delegated by the user to take action. It has a separate identity recorded in the token. An example of this is an AI agent that makes requests on behalf of Dan Moore, but isn't acting *as* Dan Moore. In the delegation case you also might have downscoped access and capture delegation history in the token.

There's also a third use case mentioned less prominently in the RFC, cross-domain token translation. This is when you get a token from one trust domain, say a partner’s identity provider or a different cloud’s issuer, and trade it for one your own system will accept. You’re translating credentials across a trust boundary, which sounds neat. But then you've also got to decide how much you trust the party on the other side to have vouched for that user.

## AI AI AI

How does token exchange matter for AI? Many AI use cases I see right now come down to an agent doing something on a user’s behalf in a system where the user has an identity but the agent does not: read my calendar, file a ticket, pull a record from my CRM. 

MCP is the plumbing for those interactions, and it’s useful (I’m a little bit cynical about the hype, but the problem is real). But MCP specifies that you shouldn't pass the token from the MCP server to downstream services. You want to [avoid token passthrough](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#token-passthrough).

So, every MCP tool call is an authorization decision. Whose identity is the agent using, and does its token grant access to one calendar or everything that particular user can touch? 

My guess is a lot of MCP servers are handing the agent a broad token based on the user's authority because it was the fastest way to get the demo working. 

If your agent got talked into doing something it shouldn’t have, what’s the worst thing its token lets it do? This is where token exchange comes in. Even if you aren't using MCP and are using direct API calls, having auditable, policy-driven token exchange can decrease the blast radius of any credential leakage.

With respect to RFC 8693, there are a few interesting holes in the specification that need to be filled out to deliver a useful service. Aside: I think this is true of RFCs in general. They're fantastic for defining interfaces and for interoperability, but there's implementation detail that's necessarily left out of an RFC. But the implementation details are really important. It's like the [authentication part of OAuth](/articles/oauth/why-no-authentication-in-oauth); critical but undefined.

Here are three holes in the RFC:

* the trust policy between the exchanger, the subject and the actor
* the policy engine that makes the delegation decision
* the audit trail that tracks decisions

### The trust policy

If you implement everything in the RFC for delegation, the authorization server has to reason about the exchanger making the request to the authorization server, the subject whose authority is being used, and the actor named in the token who is going to present it to other systems. There are three trust relationships to enforce and three questions to answer:

* Can this client exchange this subject’s token?
* Can this client present this actor?
* Can this actor act for this subject?

Each one is a place for the policy to be wrong. It's also more complexity to model, and another thing for an implementor to configure and audit.

One option to simplify things is to use the client as the actor. This is spec compliant because the `actor_token` is optional. This simplifies the trust policy. Now you have two parties and one question: is this client allowed to act on behalf of this subject, for this audience and resource? This works for many situations, such as an MCP server calling an API on behalf of a user.

The downside is that the actor now must always be a client. Anything that needs to show up in `act` needs its own client identity rather than riding on a shared service's credentials. An MCP gateway is an example of such a shared service.

### The policy engine

The policy engine determines what happens when you present a token to an authorization server in hopes of an exchange. You say "Hey, I have this token that I somehow got, and I want to exchange it for a new token with a different audience and different attributes."

The RFC explicitly refers to policy decisions, but doesn't dictate anything about how they are arrived at. From [section 2.2.1](https://datatracker.ietf.org/doc/html/rfc8693#name-successful-response):

> If the request is valid and meets all policy and other criteria of the authorization server, a successful token response is constructed...

There are three possible answers from a policy engine:

1. **No.** The authorization server says you cannot exchange this token for this particular audience, with these attributes.
2. **Yes.** Here is the token with what you asked for.
3. **Yes, but.** You'll get a token, but some of the attributes will change. Maybe it expires sooner, or the permissions in the token get downscoped.

Supporting this logic in a way that scales, is easy to administer, and that's flexible is critical to the token exchange being actually useful. But this behavior is not covered by the RFC. At FusionAuth we've approached this in two different ways, with both code and a network graph. RFC 8693 implementers must figure out how the authorization server determines one of those three outcomes whenever a client asks for a token exchange.

### The audit trail

Once you have a "no"/"yes"/"yes, but" decision from a policy engine, make sure you're recording the details of the exchange. Because token exchange is used by AI agents and other software, the auditing needs to handle a high frequency of requests.

You also need to capture the exchange details, including the audience, token details, and the policy decision. You also should make sure you can retain these records for however long your compliance department wants, in whatever storage mechanism is best.

## What RFC implementations need

The trust decisions, policy engine and audit trail are all needed to make the exchange mechanism safe and useful. The RFC acknowledges the trust decision and the policy decision, but specifies neither in detail.

As I mentioned at the beginning, not every system needs the token exchange. Here's a hypothetical to help you decide. If your reporting service were compromised today, what could the attacker do with the token it’s holding? Token exchange doesn’t make that question disappear, but it does mean the answer is "read some reports" instead of "anything the user could do."

And if someone did try for more, who would find out?
