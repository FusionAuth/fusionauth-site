The October [2026 DHS data breach](https://www.npr.org/2026/10/28/nx-s1-6021497/dhs-hack-ice) exposed information about more than 40,000 Department of Homeland Security employees and contractors. The attackers claimed to have accessed the data through DHS's Okta-based single sign-on (SSO) environment, although the method of access remains unverified.

While the incident involved workforce identities, it raises important security questions for [customer identity and access management (CIAM)](/articles/ciam/what-is-ciam) teams as well. How do you limit what authenticated users can access? What happens when credentials or sessions are compromised? And how can you detect suspicious activity after a successful login?

{/* more */}

Here are five SSO security lessons developers can apply to protect customer-facing applications:

1. [Enforce authorization beyond SSO authentication](#1-enforce-authorization-beyond-sso-authentication): A successful login is not enough; applications must still verify permissions for every protected action and resource.
1. [Limit exposure of sensitive identity data](#2-limit-exposure-of-sensitive-identity-data): Treat roles, group memberships, organizational relationships, and related metadata with the same care as other sensitive data.
1. [Enforce tenant boundaries at the application level](#3-enforce-tenant-boundaries-at-the-application-level): Prevent an authenticated user from accessing resources that belong to another customer organization.
1. [Ensure compromised access can be revoked](#4-ensure-compromised-access-can-be-revoked): Sessions and tokens must be revocable quickly when an account is compromised.
1. [Monitor suspicious activity after authentication](#5-monitor-suspicious-activity-after-authentication): Watch for unusual patterns of data access or privilege use after a valid login.

Then use the [SSO security checklist](#sso-security-checklist-for-application-developers) to identify potential weaknesses in authentication, authorization, tenant isolation, session management, and monitoring.

## 1. Enforce Authorization beyond SSO Authentication

[Single sign-on (SSO)](/glossary/single-sign-on-sso) allows users to authenticate through a centralized identity provider and access connected applications. This process establishes who the user is, but each application must still determine what that user is allowed to access or do. That's the distinction between authentication and authorization. Without properly enforced application-level permissions, a valid login can provide access to restricted information or functions.

The scale of the DHS data breach raises an important question for CIAM developers: How much sensitive information could someone access through a single authenticated identity? Answering that question requires examining the permissions enforced by individual applications, not just the authentication controls provided by SSO.

An incident involving an Australian gym booking system illustrates this risk. In August 2026, [ABC News reported](https://www.abc.net.au/news/2026-08-10/ai-assistant-hacks-gym-website-aus-cyber-attack/107007986) that a gym member's AI assistant discovered it could bypass booking restrictions and cancel another member's reservation. The assistant had been asked to book a class, but it went further, exploiting an API that lacked authorization checks to remove someone ahead of its user on the waitlist.

The booking system allowed the assistant to perform an action its user wasn't authorized to take. The vulnerability existed at the application level, where permissions should have prevented one member from changing another member's reservation. The same principle applies to applications using SSO: Successfully authenticating a user doesn't eliminate the need to enforce authorization for every protected action.

Developers should review whether their applications:

* Verify that users have permission to perform the requested action, rather than relying solely on successful authentication.
* Enforce authorization on the server for every protected application function and API endpoint.
* Apply least-privilege access and deny requests when authorization cannot be established.
* Prevent users from accessing restricted functions or modifying other users' resources through direct API calls.
* Reevaluate permissions when roles, organizational memberships, or account status change.

Different applications may require different [authorization models](/articles/identity-basics/authorization-models), including [role-based access control](/permify-docs/modeling-guides/rbac) (RBAC), [attribute-based access control](/permify-docs/modeling-guides/abac) (ABAC), and [relationship-based access control](/permify-docs/modeling-guides/rebac) (ReBAC).

The lesson for CIAM developers is to test whether application-level permissions are consistently enforced, including when authenticated users attempt to access functions or resources beyond their assigned privileges.

## 2. Limit Exposure of Sensitive Identity Data

Identity information requires the same careful access controls as other sensitive application data. The DHS breach demonstrates how revealing organizational relationships and access-related metadata can create security risks, even when the exposed records do not include passwords.

According to [reporting by WIRED](https://www.wired.com/story/massive-leak-exposes-41000-homeland-security-workers-including-undercover-ice-agents), the DHS dataset included job titles, supervisors, group memberships, and references to sensitive government operations. That information could help identify individuals with particular responsibilities, reveal organizational relationships, or support targeted impersonation attempts.

The risks of exposing metadata extend beyond identity records. In August 2026, data catalog provider Alation [confirmed a cyberattack](https://itnerd.blog/2026/08/21/ai-data-giant-alation-confirms-cyberattack/), although the company did not disclose whether data was stolen. The incident raised concerns about the potential exposure of data catalog metadata, which can reveal where sensitive information is stored, how systems are connected, and which accounts have access. As [FusionAuth's Dan Moore explained](https://www.cybersecurity-insiders.com/why-a-data-catalog-breach-is-different-and-why-you-cant-just-rotate-your-way-out-of-it/), that knowledge can remain useful to attackers long after a breach because organizations can't simply rotate credentials to erase what an attacker has learned about their systems.

The same concerns apply to identity metadata in customer-facing applications. A B2B SaaS platform might store customer organizations, account administrators, assigned roles, group memberships, and access to specific services. Exposing those details unnecessarily can help attackers identify valuable accounts, understand organizational relationships, and determine where to focus subsequent attacks.

Identity metadata can also be exposed through APIs and tokens. For example, applications may include human-readable information about roles or group memberships in ID tokens or access tokens. Signed JSON Web Tokens (JWTs) protect the integrity of their contents, but their payloads are generally readable by anyone who possesses the token unless the contents are separately encrypted. Developers should follow [secure JWT practices](/articles/tokens/building-a-secure-jwt) to avoid exposing sensitive information through token claims.

Developers should therefore minimize the information exposed through identity interfaces rather than assuming that identity metadata is harmless.

Specific actions include:

* Audit data returned through user profile endpoints, directory integrations, and administrative APIs.
* Include only the claims needed by each application or API in ID tokens and access tokens.
* Limit access to group memberships, administrative roles, and organizational relationships. Use non-readable values like UUIDs to represent them if they must be placed in a token.
* Check whether logs, analytics tools, or error reports unnecessarily capture identity attributes or tokens.
* Apply elevated authorization controls to endpoints that list users, groups, and account relationships.

Pay particular attention to bulk retrieval. An endpoint that legitimately returns identity metadata to administrators can become a significant exposure point if permissions are too broad or unusual requests go undetected.

CIAM teams should know which identity attributes their applications expose, who can retrieve them, and whether those permissions are appropriate for the sensitivity of the information.

## 3. Enforce Tenant Boundaries at the Application Level

A user authenticated through SSO must remain restricted to the customer organizations and resources they're authorized to access. In multi-tenant applications, failing to enforce these boundaries can turn a single compromised account into a much larger data exposure.

The breadth of the DHS data exposure underscores the importance of limiting access across organizational boundaries. For multi-tenant SaaS applications, that means ensuring an authenticated user cannot access resources belonging to another customer organization.

Consider a project management application serving hundreds of companies. Each customer has its own users, projects, and billing information, but all authenticate through shared identity infrastructure.

An authenticated user requests a project through an API:

```http
GET /api/projects/12345
```

If the application verifies that the user is logged in but fails to check whether they belong to the organization that owns project 12345, changing the project ID could expose another customer's information.

This vulnerability is known as [Broken Object-Level Authorization](/blog/dji-token-auth) (BOLA). Authentication may function exactly as intended while the application exposes resources to unauthorized users. This seems simple, but you must enforce this for every tenant-scoped resource.

The lesson for CIAM teams is to enforce tenant membership and resource-level permissions independently for every relevant request.

Developers should:

* Derive tenant context from trusted, validated identity and membership information.
* Verify that the user is authorized to access the requested tenant and resource.
* Treat tenant IDs in URLs, headers, or request bodies as untrusted until validated.
* Scope database queries to resources belonging to authorized tenants.
* Test horizontal privilege escalation and cross-tenant access using accounts with valid credentials.
* Explicitly evaluate permissions when users belong to multiple customer organizations.

Federated SSO adds another consideration. When customers authenticate through their own identity providers, the application must correctly associate each external identity with the intended local account and tenant. A valid authentication response from a trusted provider should not grant access to an unrelated organization. The application's [multi-tenant architecture](/docs/concepts/patterns/multi-tenant) also needs to account for how identities and customer environments are separated.

Strong tenant isolation limits how much damage a compromised customer account can cause. Even when an attacker obtains valid access, properly enforced boundaries should prevent that identity from retrieving another customer's resources.

## 4. Ensure Compromised Access Can Be Revoked

When an account is compromised, disabling it or resetting its password may not immediately end an attacker's access. Existing application sessions and previously issued tokens can remain valid, depending on how the application and identity system are configured.

For CIAM teams, the question is how quickly unauthorized access can be contained when an authenticated identity is compromised.

In an SSO environment, the identity provider and connected applications may maintain separate sessions. Terminating a session at the identity provider does not necessarily terminate active sessions in every application. Similarly, revoking a refresh token may prevent new access tokens from being issued without invalidating access tokens that are already in use. Understanding how [SSO logout and session management](/docs/authentication/sessions/logout-session-management) interact is essential when designing access termination procedures.

Consider a customer-facing application where an attacker has obtained a valid access token. The account owner discovers suspicious activity and changes their password. If the token remains valid for several hours and the API has no mechanism to reject it earlier, the attacker may continue accessing protected resources during that period.

[Sender-constrained tokens](/docs/authentication/oauth/dpop) offer another way to limit the damage from token theft. Unlike bearer tokens, which can be used by anyone who possesses them, sender-constrained tokens are tied cryptographically to a specific client key. [Demonstrating Proof of Possession (DPoP)](/blog/sender-constrain-access-tokens-react-app-dpop) is one approach that requires the client to prove possession of that key when accessing protected APIs. Even if an attacker steals the token, they can't reuse it because they don't have the corresponding private key.

To limit the impact of compromised credentials, sessions, and tokens, developers should review:

* **Session termination:** Determine whether disabling an account or ending an SSO session also terminates sessions in connected applications.
* **Access-token expiration:** Set token lifetimes according to the sensitivity of protected resources and the potential impact of token theft.
* **Token revocation:** Understand which tokens can be revoked immediately and which may remain valid until expiration.
* **Token theft protection:** Consider sender-constrained tokens to reduce the risk of stolen access tokens being reused by unauthorized clients.
* **Refresh-token protection:** Use secure storage, rotation, and reuse detection where appropriate to reduce the risk of continued unauthorized access.
* **Incident response:** Test how quickly the organization can identify affected sessions, terminate access, and prevent additional token issuance.

These controls should be tested together during security reviews and incident-response exercises. The [NIST session management guidance](https://pages.nist.gov/800-63-4/sp800-63b/session/) provides additional recommendations for session lifetimes, reauthentication, and termination.

The objective is to minimize the time an attacker can continue using compromised access, balanced with performance and usability concerns. You want to ensure that security teams understand the steps required to terminate it across connected applications.

## 5. Monitor Suspicious Activity after Authentication

A successful SSO login doesn't guarantee that subsequent activity is legitimate. If attackers obtain valid credentials or an active session, they may be able to access sensitive information without generating failed-login attempts or other authentication alerts.

The scale of the DHS data breach raises a useful question for CIAM teams: Would you know if an authenticated account began systematically collecting sensitive information from your application? Detecting that behavior requires visibility into what users do after they sign in.

Consider a customer service application where employees are authorized to look up customer accounts to resolve support issues. An employee normally accesses 20 or 30 records during a shift. If that account suddenly begins retrieving thousands of customer profiles, each individual request might be authorized, but the overall pattern could indicate compromised credentials or misuse of legitimate access.

Authentication logs alone won't reveal this behavior because it takes place within the application. Applications need to capture relevant authorization decisions and API activity, then identify patterns that warrant investigation. User and entity behavior analytics (UEBA) can help detect deviations from normal activity, while [identity monitoring and audit logs](/docs/deploy/monitor) provide additional context for investigating suspicious access.

Developers should review whether their applications can:

* **Detect unusual data access:** Identify unexpected increases in record retrieval, bulk exports, or systematic attempts to enumerate customer accounts.
* **Correlate activity with identities:** Associate sensitive API requests with authenticated users, sessions, and relevant tenant context.
* **Monitor privilege changes:** Track administrative actions, role assignments, and changes to permissions that could expand access.
* **Identify unauthorized access attempts:** Alert on repeated authorization failures or attempts to access resources outside an account's permitted scope.
* **Support incident response:** Provide sufficient audit history to determine which accounts accessed sensitive information, what resources were involved, and when the activity occurred.

Monitoring thresholds should account for legitimate differences in customer behavior. A large enterprise may routinely process far more requests than a small business, and scheduled data exports may be normal for some accounts.

Organizations should also consider how risk changes throughout an authenticated session. Unusual activity, changes in device or network context, and attempts to access sensitive resources can all warrant reevaluating a user's risk level. Depending on the severity, applications may need to require additional authentication, restrict access, or terminate a session.

The lesson for CIAM developers is to monitor activity throughout the session and ensure suspicious behavior can trigger an appropriate response. Testing these controls helps determine how effectively an application can detect and contain misuse of otherwise legitimate access.

## SSO Security Checklist for Application Developers

The DHS data breach provides an opportunity to review how customer-facing applications protect authenticated access. Use this checklist to identify potential weaknesses in your SSO implementation.

**Authentication and authorization**

* [ ] Does your application check user permissions before allowing access to protected features, data, and API endpoints?
* [ ] Are permissions checked against the requested resource and action?
* [ ] Can authenticated users access administrative functions or other users' data by modifying API requests?

**Identity data exposure**

* [ ] Do tokens and identity APIs expose only necessary user attributes?
* [ ] Are organizational relationships, roles, and group memberships appropriately restricted?
* [ ] Are bulk identity-data retrieval functions protected and monitored?

**Tenant isolation**

* [ ] Is tenant membership verified server-side for tenant-scoped resource requests?
* [ ] Has cross-tenant access control been tested using valid accounts from different organizations?
* [ ] Are federated identities correctly associated with local users and tenants?

**Sessions and tokens**

* [ ] Are token lifetimes and session expiration policies appropriate for the protected resources?
* [ ] Can compromised sessions and tokens be immediately invalidated, or is there a clearly defined limit on how long they remain usable?
* [ ] Are users required to verify their identity again before performing sensitive actions, such as changing account recovery information or exporting customer data?

**Monitoring and response**

* [ ] Can authentication events be linked to sensitive activity within applications and APIs?
* [ ] Are unusual data access patterns, changes to user permissions, and unauthorized access attempts monitored?
* [ ] Has the process for identifying compromised accounts and terminating their access been tested?

## Applying the DHS Lessons to Customer Identity Security

The precise cause of the DHS data breach remains unconfirmed, but the reported exposure demonstrates the potential consequences of unauthorized access to sensitive identity information.

For CIAM teams, the incident provides an opportunity to examine how customer-facing applications protect authenticated access. That includes enforcing permissions at the application level, protecting sensitive identity information, maintaining tenant boundaries, limiting the duration of compromised access, and monitoring for suspicious activity.

Understanding [how SSO works](/articles/authentication/how-sso-works), including which security responsibilities belong to the identity provider and which belong to individual applications, can help developers identify gaps in their implementations. The next step is to test whether those protections actually hold when an authenticated account is compromised or misused.

## Frequently Asked Questions

### What Can CIAM Teams Learn from the DHS Data Breach?

The DHS data breach teaches CIAM teams about the importance of controlling what authenticated users can access and what identity information applications expose. CIAM teams should review application authorization, tenant isolation, session management, identity-data protection, and monitoring.

### What Are the Biggest Security Risks of Single Sign-On?

SSO security risks include compromised credentials, stolen sessions or tokens, excessive permissions, and insufficient application-level authorization. Because SSO enables access to multiple connected applications, misused credentials or sessions may affect several systems. Developers can reduce these risks through strong authentication, least-privilege authorization, secure token handling, and monitoring.

### How Can Developers Secure SSO Implementations?

Developers can secure SSO implementations by using established protocols such as OIDC, correctly validating tokens, and enforcing authorization within each application and API. Additional protections include phishing-resistant MFA where appropriate, secure session management, limited token lifetimes, effective revocation mechanisms, and monitoring of suspicious authenticated activity.

### How Does CIAM Prevent Unauthorized Access to Customer Data?

Customer identity and access management (CIAM) helps prevent unauthorized access by verifying user identities, supporting multi-factor authentication (MFA), and managing user roles and permissions. Applications must then enforce those permissions to ensure users can access only the data and functions they're authorized to use. In multi-tenant environments, this includes validating tenant membership and resource ownership to prevent customers from accessing another organization's data.

### What Is the Difference between SSO Authentication and Application Authorization?

SSO authentication establishes a user's identity through a trusted identity provider, allowing them to sign in to connected applications. Application authorization determines which resources and actions the authenticated user can access. For example, SSO may verify that someone is a legitimate customer, while application authorization determines whether they can view billing records, manage users, or change account settings.
